Week 6 · Architecture & Governance

Architecture & Governance

รายละเอียดเชิงลึกของการออกแบบสถาปัตยกรรมระบบเป้าหมาย (To-Be Architecture), การกำหนดมาตรฐานการสื่อสารและกฎเกณฑ์การทำงาน (DoR/DoD) รวมถึงการวิเคราะห์ผลต่างงบประมาณด้วยหลักการ EVM

1. To-Be Architecture (การออกแบบสถาปัตยกรรมระบบเป้าหมาย)

เพื่อแก้ไขปัญหาจากระบบเดิมที่เป็น Monolithic Script ซึ่งใช้งานไฟล์ JSON และมีปัญหาเรื่องการผูกติดกับ Global State สถาปัตยกรรมใหม่ถูกออกแบบโดยมุ่งเน้นที่การแยกส่วนประกอบ (Separation of Concerns) และรองรับการขยายตัว (Scalability) ดังนี้:

  • SQLiteDatabaseContext (Singleton Pattern):
    • ปัญหาที่แก้: ลดปัญหา Database/File Locked เมื่อมีผู้ใช้งานหรือคำสั่งพยายามเขียนไฟล์พร้อมกัน
    • วิธีการทำงาน: ควบคุมให้มีจุดเชื่อมต่อ (Connection) ไปยังฐานข้อมูล SQLite เพียงจุดเดียวตลอดการทำงานของโปรแกรม ทำให้สามารถจัดการ Transaction (Commit/Rollback) ได้อย่างมีประสิทธิภาพ
  • InventoryRepository (Repository Pattern):
    • ปัญหาที่แก้: แยกคำสั่ง SQL ออกจาก Business Logic เพื่อให้ง่ายต่อการทดสอบและดูแลรักษา
    • วิธีการทำงาน: ครอบการทำงานของฐานข้อมูลทั้งหมด (CRUD) ไว้ในคลาสเดียว และบังคับใช้ Parameterized Queries เพื่อป้องกันการถูกโจมตีผ่าน SQL Injection อย่างเด็ดขาด
  • MemberTier (Strategy Pattern):
    • ปัญหาที่แก้: โค้ดเดิมมีการใช้ if-else ซ้อนกันจำนวนมากในการคำนวณส่วนลด ซึ่งยากต่อการเพิ่มระดับสมาชิกใหม่
    • วิธีการทำงาน: สร้าง Interface หรือ Base Class สำหรับ Member และสืบทอดเป็น Regular, Silver, Gold, Platinum โดยแต่ละคลาสจะรับผิดชอบในการคืนค่าอัตราส่วนลด (Discount Rate) ของตัวเอง ทำให้การเพิ่มสมาชิกระดับใหม่ในอนาคต (เช่น Diamond) สามารถทำได้โดยไม่ต้องแก้ไขโค้ดเดิม (Open/Closed Principle)

2. Communication Matrix และ DoR / DoD

การกำหนดกรอบการสื่อสารและมาตรฐานการทำงานร่วมกันภายในทีม (Project Manager, QA/Tester, Tech Lead) เพื่อให้การบริหารจัดการโครงการด้วย Trello และ GitHub เป็นไปอย่างราบรื่น:

การอัปเดตงานประจำวัน (Standup)
ช่องทาง: Discord Voice | ความถี่: ทุกเย็น (15 นาที) | ผู้ดูแล: Project Manager
Definition of Ready (DoR)
ก่อนที่ Developer จะเริ่มดึงงานจาก Trello ไปทำ การ์ดงานนั้นต้องมีองค์ประกอบครบถ้วน:
  • ระบุเป้าหมายและฟีเจอร์อย่างละเอียด (Description)
  • ประเมินความเสี่ยงและจุดกระทบ (Hotspots) ที่อาจทำให้ระบบเดิมพัง
  • มีการมอบหมายผู้รับผิดชอบ (Assignee) อิงตาม RACI Matrix (Responsible, Accountable)
  • สร้าง Branch ใน GitHub เตรียมพร้อมสำหรับการพัฒนา โดยแยกออกจากกิ่งหลัก (Develop)
Definition of Done (DoD)
งานจะถูกย้ายไปยังช่อง "Done" ได้ก็ต่อเมื่อผ่านเงื่อนไขคุณภาพสูงสุด:
  • ผ่านการตรวจสอบโค้ด (Code Review) จาก Tech Lead เพื่อรักษามาตรฐานความสะอาดของโค้ด (เช่น PEP 8)
  • ต้องรันสคริปต์ test_app.py ที่สร้างโดย QA ผ่านแบบ 100% (No Error, No Warning) บน CI/CD Pipeline
  • Merge โค้ดเข้ากิ่งหลักสำเร็จโดยไม่มีข้อขัดแย้ง (Merge Conflict)

3. การวิเคราะห์ผลต่างงบประมาณ (Cost Variance Analysis - EVM)

ตัวอย่างการนำหลักการ Earned Value Management (EVM) มาใช้ประเมินสถานการณ์และควบคุมงบประมาณ เมื่อพบปัญหาเฉพาะหน้า:

  • สถานการณ์: งานแปลงระบบจัดเก็บข้อมูลจาก JSON เป็น SQLite (มอบหมายให้ Developer)
  • Planned Cost (งบที่ตั้งไว้): ประเมินเวลาไว้ที่ 6 ชั่วโมง (อิงเรต 400 บาท/ชม.) รวม 2,400 บาท
  • Earned Value (มูลค่างานที่ทำเสร็จ): งานถูกดำเนินการจนเสร็จสิ้นและผ่านการทดสอบ 100% คิดเป็นมูลค่า 2,400 บาท
  • Actual Cost (ต้นทุนจริง): Developer พบว่าโครงสร้างข้อมูลเก่าใน JSON (Spaghetti Code) มีความซับซ้อนและไม่มีมาตรฐาน จึงต้องเสียเวลาแกะโค้ดและ Refactor เพิ่มเติม ทำให้ใช้เวลาจริงไป 10 ชั่วโมง คิดเป็นต้นทุน 4,000 บาท
  • การคำนวณ CV (Cost Variance): CV = EV - AC = 2,400 - 4,000 = -1,600 บาท
  • การจัดการความเสี่ยง (Management Action):
    1. แจ้งเตือน (Warning) สถานะ Over Budget ให้ทีมทราบ
    2. Project Manager ทำเรื่องดึงเงินจากงบสำรอง (Contingency Reserve) ที่ตั้งไว้ 15% ของโครงการมาชดเชยส่วนต่าง 1,600 บาท
    3. เรียกประชุมด่วนกับ Tech Lead เพื่อปรับปรุง Blueprint ในฟีเจอร์ถัดไป (เช่น ระบบสมาชิกระดับ Platinum) ให้รัดกุมยิ่งขึ้น เพื่อป้องกันการประเมินเวลาพลาดในอนาคต
