สัปดาห์ที่ 6: เกณฑ์การสื่อสาร DoR/DoD และสถาปัตยกรรม To-Be

กำหนดตารางการสื่อสารภายในทีม (Communication Matrix), เกณฑ์ DoR/DoD, กรณีศึกษาผลต่างงบประมาณ (Cost Variance) และสถาปัตยกรรม To-Be

เปิดสไลด์ประกอบสัปดาห์ 6 →

1. ตารางการสื่อสารภายในทีม (Communication Matrix)

หัวข้อ / วัตถุประสงค์ ช่องทาง ความถี่ ผู้รับฟัง ผู้รับผิดชอบ
อัปเดตงานประจำวัน (Standup) Discord Voice / Chat ทุกเย็น (15 นาที) สมาชิกทุกคนในทีม Project Manager
การแจ้งบั๊ก / ทดสอบไม่ผ่าน การ์ดบน Trello ทันทีที่พบปัญหา ผู้เขียนโค้ดฟีเจอร์นั้นๆ QA / Tester
ขอ Review Code ก่อน Merge GitHub PR / Discord เมื่อสร้าง PR เสร็จ สมาชิกทีมที่เกี่ยวข้อง Tech Lead
ติดตามความคืบหน้าภาพรวม Trello Board อัปเดตตลอดเวลา สมาชิกทุกคนและอาจารย์ สมาชิกทุกคน

2. เกณฑ์ความพร้อมและความสำเร็จ (DoR vs DoD)

Definition of Ready (DoR): ก่อนดึงการ์ดงานมาทำ ต้องมีรายละเอียดชัดเจน, ผ่านการประเมิน Hotspot, มีการระบุบทบาท RACI (R และ A) และแตก Branch ออกจาก develop

Definition of Done (DoD): งานจะเสร็จสมบูรณ์เมื่อผ่านการตรวจ Code Review จาก Tech Lead ตามมาตรฐาน PEP 8, ผ่าน Automated Tests 100%, รวมโค้ดเข้าสายหลัก และจัดทำเอกสารสรุปผลเรียบร้อย

3. กรณีศึกษาการวิเคราะห์ผลต่างงบประมาณ (Cost Variance Analysis)

ข้อมูลสมมติเพื่อการเรียน · Fictional Educational Data

การวิเคราะห์ตามหลักการ EVM ในเอกสาร Cost_Variance_Analysis.md เพื่อควบคุมต้นทุน:

  • มูลค่างานที่ทำเสร็จ (EV): 2,400 บาท (ประมาณการ 6 ชม. × 400 บาท/ชม.)
  • ต้นทุนจริงที่เกิดขึ้น (AC): 4,000 บาท (เกิดปัญหาข้อมูลเก่าทำให้ใช้เวลา 10 ชม. × 400 บาท/ชม.)
  • ผลต่างงบประมาณ: $CV = EV - AC = 2,400 - 4,000 = -1,600$ บาท (เกินงบประมาณ)

แนวทางบริหาร: PM แจ้งเตือนความเสี่ยง ดึงเงินสำรอง Contingency Reserve มาชดเชย และปรึกษา Tech Lead เพื่อทบทวนการออกแบบ Blueprint ป้องกันการแก้โค้ดซ้ำซ้อน

4. สถาปัตยกรรม To-Be (แบบออกแบบเท่านั้น)

DESIGN ONLY
สถานะสถาปัตยกรรม To-Be: ในเอกสาร To_Be_Architecture.md มีการระบุสถาปัตยกรรมคลังสินค้าใหม่ที่รวม SQLite, โมดูลระบบสมาชิก (Member Tier) และระบบคำนวณเงินสด (Checkout Engine) ซึ่งทั้งหมดในสัปดาห์นี้ยังคงเป็นแบบออกแบบเท่านั้น (Design-only) ยังไม่มีการเขียนโค้ดจริงใน Sprint 1
