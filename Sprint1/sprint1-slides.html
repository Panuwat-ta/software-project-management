สรุป Sprint 1
ระบบจัดการสินค้าคงคลังแบบ CLI

การปรับโครงสร้างระบบ การทดสอบ การควบคุมการเปลี่ยนแปลง และสถานะพร้อมปล่อยที่ตรวจสอบย้อนกลับได้

ENGSE202 / ENGSE225ตัวเลขแผนงานและ EVM เป็นข้อมูลสมมติเพื่อการเรียน

ขอบเขตการนำเสนอและหลักฐาน

แยกข้อเท็จจริงจากโค้ดและเอกสาร ออกจากตัวเลขที่ใช้เป็นกรณีศึกษาในรายวิชา

  • เป้าหมาย: ลดความเสี่ยงจาก global state, ตรวจข้อมูลนำเข้า และบันทึก JSON แบบ atomic
  • ผลผลิตที่ตรวจได้: โค้ด refactor, ชุดทดสอบ, เอกสารควบคุมการเปลี่ยนแปลง และ checklist ปล่อยงาน
  • ขอบเขตที่ไม่กล่าวอ้างว่าเสร็จ: SQLite, Member และ Checkout อยู่ในสถานะออกแบบหรือ backlog

เกณฑ์ความน่าเชื่อถือ

ทุกข้อสรุปอ้างอิงจาก sprint1.md และเอกสาร W1–W12 หากหลักฐานการอนุมัติยังไม่มี จะระบุว่า “คงค้าง” แทนการสรุปว่าเสร็จแล้ว

แหล่งหลัก: Sprint1/sprint1.md §1, §4, §8–§122 / 12

เส้นทางหลักฐานตลอด W1–W12

แต่ละช่วงสร้างหลักฐานคนละชนิด ตั้งแต่ปัญหาเดิมจนถึงการเตรียมตรวจรับ

W1–W4
วิเคราะห์และปรับโครงสร้าง

  • Charter, scope และความเสี่ยงของระบบเดิม
  • DFD, hotspot และ static analysis
  • แยก Product, InventoryManager และ CLI
  • ยืนยันพฤติกรรมหลักด้วย PyTest

W5–W8
วางแผนและควบคุมการเปลี่ยนแปลง

  • ประเมินสถาปัตยกรรม คุณภาพ และงบ
  • กำหนด communication matrix กับ DoD
  • ตั้ง cost baseline และ quality gate
  • วิเคราะห์ CR-01 ก่อนนำเข้า backlog

W9–W12
วัดผล ทำให้แข็งแรง และเตรียมปล่อย

  • EVM, retrospective และการส่งต่องาน
  • CCB สำหรับ CR-02 และแก้ BUG-101
  • Hardening, scope freeze และ UAT plan
  • Final EVM, changelog และ release checklist

สถานะความพร้อมก่อนปล่อย

การทดสอบผ่านช่วยยืนยันพฤติกรรมของโค้ด แต่ยังแทน formal acceptance และ release governance ไม่ได้

ด่านตรวจ สถานะ หลักฐานและงานที่เหลือ
Regression test ผ่านแบบระบุไฟล์ 5 passed สำหรับ refactor และ 25 passed สำหรับ Week 12
UAT 3 scenarios รอลงนาม มี scenario SC01–SC03 แต่ช่องผลและลายเซ็น formal acceptance ยังว่าง
Release tag ยังไม่มี CHANGELOG เตรียมไว้ แต่พบ tag v1.0.0 เท่านั้น ยังไม่มี v2.0.0-evolution
Code quality gate มีหนี้เทคนิค Bandit สะอาดตามรายงาน แต่ Flake8 ยังมี line-length E501
แหล่ง: sprint1.md §5, §8, §10–§12; UAT_Sign_Off_Sheet.md; Release_Checklist.md11 / 12

เส้นทางการสาธิตในชั้นเรียน

  1. เริ่มจากความเสี่ยงของโค้ดเดิมและขอบเขตที่ทีมตกลงกัน
  2. อธิบายการ refactor และหลักฐานการทดสอบแบบรันซ้ำได้
  3. สรุปการตัดสินใจ CR, EVM และบทเรียนการบริหารงาน
  4. ปิดด้วย release gate ที่ยังต้องทำก่อนส่งมอบอย่างเป็นทางการ

ข้อสรุป: มีหลักฐานสำหรับโค้ด การทดสอบ และเอกสารควบคุมงาน ขณะที่ UAT sign-off, lint ที่คงค้าง และ Git tag ต้องปิดให้ครบก่อนเรียกว่า release สมบูรณ์
