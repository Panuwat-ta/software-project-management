สัปดาห์ที่ 1: ขั้นวางแผนและทบทวนโค้ดดั้งเดิม (Planning & Legacy Code Review)

จัดทำกฎบัตรโครงการ (Project Charter) กำหนดบทบาทหน้าที่ วางกรอบขอบเขตงาน (Scope) และวิเคราะห์ความเสี่ยงเริ่มต้นของระบบเดิมใน app_v1.py

เปิดสไลด์ประกอบสัปดาห์ 1 →

1. กฎบัตรโครงการ (Project Charter Highlights)

จัดทำขึ้นเพื่อกำหนดกรอบการบำรุงรักษาและปรับปรุงระบบจัดการคลังสินค้าแบบ CLI โดยระบุเป้าหมาย 4 ด้านหลัก:

  • ปรับปรุงเสถียรภาพ (Stability): ป้องกันระบบแครชจากการกรอกข้อมูลผิดประเภท (เช่น ตัวอักษรปนในช่องตัวเลข) และป้องกันการใส่ค่าติดลบ
  • ปรับปรุงโครงสร้าง (Refactoring): กำจัดตัวแปร Global Mutable State (x, db) และเปลี่ยนชื่อตัวแปรย่อเป็นชื่อที่มีความหมายชัดเจนตามมาตรฐาน PEP 8
  • รักษาความสมบูรณ์ของข้อมูล (Data Integrity): ป้องกันไฟล์ข้อมูลเสียหายเมื่อเกิดเหตุไฟฟ้าดับหรือระบบหยุดทำงานกะทันหันขณะบันทึก
  • สร้างระบบทดสอบอัตโนมัติ (Automated Testing): พัฒนาชุดทดสอบ Regression Tests ด้วย PyTest

2. ขอบเขตการทำงาน (In-Scope vs Out-of-Scope)

สิ่งที่อยู่ในขอบเขต (In-Scope) สิ่งที่อยู่นอกขอบเขตเด็ดขาด (Out-of-Scope)
• ดักจับ Input Validation และ Exception Handling (ราคา, สต็อก) • การพัฒนา GUI (Graphical User Interface) หรือหน้าเว็บแอปพลิเคชัน
• เปลี่ยนชื่อตัวแปรที่กำกวม (x, db, a, b, c, d, e) • การเปลี่ยนเทคโนโลยีฐานข้อมูลเป็น SQL/NoSQL ภายนอกในเฟสแรก
• แยก Business Logic ออกจาก CLI Presentation Layer • การเพิ่มระบบชำระเงินออนไลน์หรือโมดูลภายนอกที่ไม่เกี่ยวข้อง
• การบันทึกไฟล์ด้วยกระบวนการ Safe Atomic Write • ระบบสมาชิกหรือโปรโมชั่นลดราคา (ยังไม่อยู่ในขอบเขตการส่งมอบเฟสแรก)

3. การวิเคราะห์ข้อบกพร่องในระบบเดิม (Legacy Code: app_v1.py)

จากการตรวจสอบไฟล์ app_v1.py และ doc.md พบจุดอันตรายทางโครงสร้างที่ส่งผลกระทบโดยตรงต่อความเสถียรของระบบ:

จุดบกพร่องใน app_v1.py ผลกระทบต่อระบบ แนวทางแก้ไข
ตัวแปร Global x และ db เกิด High Coupling ทุกฟังก์ชันเข้ามารุมแก้ไขข้อมูลในหน่วยความจำโดยตรง ไม่สามารถเขียน Unit Test แยกส่วนได้ ย้ายเข้าสู่คลาส InventoryManager และใช้ Dependency Injection
การแปลงชนิดข้อมูลตรงๆ เช่น int(input()) หากผู้ใช้กรอกข้อความหรือกด Enter ข้าม โปรแกรมจะโยนข้อผิดพลาด ValueError และล่มทันที ครอบด้วยลูปรับค่าพร้อมบล็อก try-except
ไม่ตรวจสอบตัวเลขติดลบ ผู้ใช้สามารถกรอกจำนวนสต็อกหรือราคาติดลบ ทำให้ยอดมูลค่ารวมคลังสินค้าเพี้ยน เพิ่มเงื่อนไขตรวจสอบค่ามากกว่าหรือเท่ากับศูนย์ (Non-negative check)
การบันทึกทับไฟล์ JSON โดยตรง หากโปรแกรมหยุดชะงักขณะเขียนไฟล์ ข้อมูลสินค้าทั้งหมดจะสูญหายถาวร ใช้หลักการ Atomic Write (เขียนลง Temp แล้วสลับด้วย os.replace)

4. ตารางประเมินความเสี่ยงเริ่มต้น (Initial Risk Assessment)

  • ความเสี่ยงจากการพังยับเนื่องจากการเปลี่ยนโค้ด (Regression Risk): การนำตัวแปรโกลบอลออกอาจส่งผลกระทบต่อตรรกะเดิม → มาตรการ: ให้ QA สร้าง Unit Tests ครอบคลุมการทำงานเดิมก่อนเริ่มแตะต้องโค้ดโครงสร้างหลัก
  • ความเสี่ยงของโครงสร้างข้อมูลเดิมเสียหาย (Data Incompatibility): ข้อมูลเดิมใน data.json อาจไม่ตรงกับโครงสร้างใหม่ → มาตรการ: เพิ่มชั้น Default Fallback ในการโหลดข้อมูล
  • ความเสี่ยงจากการไม่มีชุดทดสอบเดิม (Lack of Tests): โค้ดตั้งต้นไม่มีเทสต์ → มาตรการ: บังคับเกณฑ์ DoD ให้ทุกชิ้นงานต้องผ่าน PyTest 100%
