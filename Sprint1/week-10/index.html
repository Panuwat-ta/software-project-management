สัปดาห์ที่ 10: คำขอฉุกเฉิน CR-02, การประชุม CCB และการแก้ไข BUG-101

กระบวนการ Fast-track Change Request CR-02 (ส่งออกรายงาน CSV), การประชุมคณะกรรมการควบคุมการเปลี่ยนแปลง (CCB) และการวิเคราะห์รากเหง้าข้อบกพร่อง BUG-101 ด้วย 5 Whys

1. คำขอเปลี่ยนแปลงฉุกเฉิน CR-02 (Emergency CSV Export)

ข้อมูลสมมติเพื่อการเรียน · Fictional Educational Data

ตามมาตรฐาน ISO/IEC 14764 เมื่อมีคำขอด่วนเพื่อนำไปเปิดใน Excel ป้องกันสินค้าขาดสต็อก ทีมต้องไม่กระโดดไปแก้โค้ดโดยไร้การควบคุม:

  • การออกแบบ: สร้างคลาสเฉพาะ CsvReportExporter ทำงานแบบ Static Method ไร้ State ไม่ผูกมัดกับ UI
  • Header ของไฟล์ CSV: ProductID,ProductName,Barcode,Quantity,ReorderPoint,Price รองรับ UTF-8
  • ประมาณการงาน (Effort): 4.5 Man-Hours (Senior Dev 2.0, Dev 1.0, QA 1.5 ชม.) คิดเป็นต้นทุน 1,350 บาท (@ 300 บาท/ชม.)
  • มติที่ประชุม CCB: อนุมัติ Option A ให้ทำใน Sprint 2 โดยดึงงบจาก Contingency Reserve จำนวน 1,350 บาท

2. การบันทึกและแก้ไขข้อบกพร่อง BUG-101 (KeyError 'barcode')

พบข้อบกพร่องเมื่อนำไฟล์ data.json สกีมาเก่าที่สร้างจากสัปดาห์ที่ 1 (ไม่มีฟิลด์ barcode) มาโหลด โปรแกรมจะเกิด Runtime Exception และล่มทันที:

5 WHYS
การวิเคราะห์สาเหตุที่แท้จริง (Root Cause Analysis):
1. ทำไมเกิด KeyError? → หาคีย์ barcode ไม่เจอ เพราะโค้ดดึงค่าตรงๆ item['barcode']
2. ทำไมหาไม่เจอ? → ไฟล์ข้อมูลเก่าสร้างจาก W1 ยังไม่มีฟิลด์นี้
3. ทำไมอ่านข้อมูลเก่าไม่ได้? → ขาดตรรกะ Migration
4. ทำไมไม่มี Fallback? → ผู้พัฒนาสันนิษฐานว่าข้อมูลต้องเป็นสกีมาใหม่เสมอ
5. Root Cause: ขาดกลไก Data Validation และ Default Fallback ในชั้น InventoryRepository

วิธีการแก้ไขที่รากเหง้า (Root Cause Fix):

# ไม่ใช้วิธีปิด Error ลอยๆ (try-except pass) แต่ใส่ Fallback ชัดเจน
code = item.get('barcode', '')
reorder_pt = item.get('reorder_point', 5)

Defect-Driven Testing: เขียน Test Case จำลองบั๊กใน test_app.py ให้รัน Fail ก่อน (RED) แล้วแก้โค้ดให้รันผ่าน (GREEN) พร้อมบรรจุเข้า Regression Suite ถาวร
