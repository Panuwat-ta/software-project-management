As-is vs To-be Architecture

วิวัฒนาการจาก Monolithic สู่ Modular Clean Architecture

แก้ปัญหาจุดเสี่ยงข้อมูลเสียหายด้วยการแยกเลเยอร์และใช้ฐานข้อมูลเชิงสัมพันธ์

ระบบเดิม (As-is Monolithic) จุดเสี่ยงสูง
  • รวมส่วนติดต่อผู้ใช้ ตรรกะธุรกิจ และการเข้าถึงไฟล์ไว้ในสคริปต์เดียว (app_v1.py)
  • พึ่งพาตัวแปรโกลบอล x และ db ขาดการห่อหุ้มข้อมูล (Data Encapsulation)
  • เขียนบันทึกทับไฟล์ JSON โดยตรง เสี่ยงข้อมูลพังเสียหายเมื่อโปรแกรมหยุดชะงัก
ระบบใหม่ (To-be Design) มาตรฐาน OOP
  • แบ่ง 3 เลเยอร์: Presentation (SystemCLI), Service และ Repository
  • จัดการฐานข้อมูลผ่าน DatabaseManager แบบ Singleton Pattern ป้องกันการแย่งใช้ไฟล์
  • รองรับ ACID Transactions ด้วย SQLite และคำนวณส่วนลดสมาชิกด้วย Strategy Pattern

ISO/IEC 25010 Quality Framework

ผลการประเมินคุณภาพตามมาตรฐาน ISO/IEC 25010

3 ด้านวิกฤตที่ต้องแก้ไขทันที (ตัวเลขจำลองเพื่อการศึกษา)

3 ด้านวิกฤตที่ต้องได้รับการแก้ไขทันที ข้อบกพร่อง
  • Reliability (ความน่าเชื่อถือ): เสี่ยงข้อมูลสูญหายสูงจากการขาดระบบ Transaction ในการเขียนไฟล์
  • Security (ความปลอดภัย): ไร้ระบบยืนยันตัวตน และบันทึกข้อมูลแบบข้อความธรรมดา (Plain-text)
  • Maintainability (การบำรุงรักษา): โค้ดรวมในไฟล์เดียว ตัวแปรไม่เป็นไปตามข้อกำหนด PEP 8
