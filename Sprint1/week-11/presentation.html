Week 11 · Hardening, Flow Metrics & Scope Freeze

Hardening & Scope Freeze

ปรับโค้ดให้แข็งแกร่ง ตัวชี้วัดการไหลของงาน และข้อตกลงการแช่แข็งขอบเขต — เตรียมระบบสู่ UAT

รวบรวมเนื้อหาครบถ้วนจากเอกสารสัปดาห์ที่ 11: Hardening Report (Code Smells, Atomic Writes, Exception Hygiene, Flake8/Bandit, Code Freeze), Flow Metrics (CFD, Little's Law, Burnup, EVM, CPI/SPI) และ Scope Freeze Agreement

1. กลิ่นโค้ดที่แก้ไขแล้ว — 3 รายการ (Hardening Report)

1.1 โค้ดซ้ำซ้อน (Duplicate Code) — ละเมิด DRY

  • ก่อนแก้: ตรรกะตรวจสอบ if product_id in products: ถูกเขียนซ้ำ ๆ ทั้งในเมนูเพิ่มสต็อก ลดสต็อก และส่งออก CSV
  • ความเสี่ยง: หากแก้เงื่อนไขไม่ครบทุกจุดจะเกิด Inconsistency
  • หลังแก้ (Extract Method): ยุบตรรกะซ้ำซ้อนเป็น Helper Method กลางใน InventoryService แล้วให้ทุกจุดเรียกใช้แทน ไม่เปลี่ยนพฤติกรรมโปรแกรม

1.2 โค้ดตาย (Dead Code) — Cognitive Load

  • ก่อนแก้: ฟังก์ชันคำนวณและตัวแปรชั่วคราวจากการทดลองใน Sprint 1 ที่ไม่ได้ใช้แล้ว บล็อกคอมเมนต์ขนาดใหญ่ที่ปิดทับโค้ดเก่า และ Speculative Generality (เขียนเผื่อฟังก์ชันอนาคตที่ยังไม่จำเป็น)
  • หลังแก้ (Delete Ruthlessly): ลบโค้ดส่วนเกินทิ้งทันที ไม่ต้องกลัวโค้ดหาย เพราะ Git Version Control บันทึกประวัติไว้ทั้งหมด 100%

1.3 การแอบใช้ข้อมูลของโมดูลอื่น (Feature Envy) — ละเมิด Information Hiding

ก่อนแก้: คลาสภายนอก (เช่น ConsoleUI หรือ CsvExporter) แอบดึงฟิลด์ของ Product มาคำนวณยอดเงินด้วยตัวเอง
หลังแก้ (Move Method): ย้ายตรรกะการคำนวณเข้าไปอยู่ในคลาสเจ้าของข้อมูล (Data Owner) ผู้เรียกส่งอาร์กิวเมนต์น้อยที่สุดแล้วใช้ค่าที่ส่งกลับมา

2. Atomic File Writing & Exception Hygiene

การเขียนไฟล์แบบอะตอมมิก (2 ขั้นตอน)

  • ปัญหา: open(..., 'w') ล้างเนื้อหาไฟล์เดิมทิ้งทันที หากไฟดับหรือ Crash ระหว่าง json.dump() ข้อมูลจะสูญหายถาวร กลายเป็นไฟล์ว่างขนาด 0 Bytes (Data Corruption Risk)
  • ขั้นตอนที่ 1 — Write to Temp: เขียนข้อมูลใหม่ลงไฟล์ชั่วคราว (.tmp) ให้เสร็จสมบูรณ์ก่อน
  • ขั้นตอนที่ 2 — Atomic Replace: สั่ง os.replace() สลับไฟล์ในระดับ OS แบบ All-or-Nothing
  • หลักประกัน: Zero Data Loss Guarantee — เขียนสำเร็จ 100% หรือรักษาไฟล์เดิมไว้ (ใช้ tempfile + os.replace)

สุขอนามัยของข้อยกเว้น — ห้าม except: pass

  • ห้ามเด็ดขาด (Anti-Pattern): try / except / pass ครอบจักรวาล (Blind Exception Swallowing) — ซ่อนระเบิดเวลา ทำให้ระบบเน่าเสียเงียบ ๆ
  • แนวทางที่ถูก (Best Practice): ระบุ Exception เจาะจง (FileNotFoundError, JSONDecodeError) บันทึก Log เพื่อการสืบสวน และแจ้งเตือนด้วยข้อความที่ปลอดภัยโดยไม่เปิดเผย Stack Trace ภายใน

3. สแกน Flake8 / Bandit & วินัย Code Freeze

ขั้นตอนสแกน Flake8 / Bandit (ตามที่สอน)

รันจากรากของรีโป:

flake8 . --count --statistics
bandit -r . -x ./tests
  • Flake8: เคลียร์ Syntax, Unused Imports และ PEP 8 ทั้งหมด เพิ่ม Analyzability และ Modifiability ตาม ISO/IEC 25010
  • Bandit: สแกนช่องโหว่ซอร์สโค้ด Python (Hardcode รหัสผ่าน/API Keys, eval()/exec(), Injection, การเปิดไฟล์ไม่ปลอดภัย) ระดับ Medium/High ต้องไม่เหลือ
สถานะ: ยังไม่ได้รันซ้ำในคอมมิตของเอกสารนี้ จึงไม่แปะผลลัพธ์ของเครื่องมือที่นี่เพื่อหลีกเลี่ยงการแต่งตัวเลข ให้บันทึกผลคำสั่งจริงลง Hardening Log / ข้อความคอมมิตเมื่อรันแล้ว และแก้ไขทุกข้อที่พบก่อน Freeze

วินัย Code Freeze (ISO/IEC/IEEE 12207:2017)

  • เหตุผล: การแก้โค้ดนาทีสุดท้าย (Last-Minute Changes) คือสาเหตุอันดับ 1 ที่ทำให้ระบบพังวันส่งมอบ
  • ห้าม: แตก Branch ฟีเจอร์ใหม่ ปรับ UI เพื่อความสวยงามส่วนตัว รับ Change Request ตัวใหม่
  • อนุญาตเฉพาะ: แก้บั๊กวิกฤต (Critical Defects) อุดช่องโหว่ตามรายงาน Bandit/Flake8 และเขียน Unit Test เพิ่มเพื่อยกระดับ Coverage
  • เงื่อนไขก่อน Freeze: ฟังก์ชัน Sprint 2 (CR-01 Barcode + CR-02 CSV Export) เสร็จ 100% ประกาศระงับ Feature Branch ใหม่ เตรียมระบบสู่ UAT ใน Week 12

4. CFD Anatomy, Little's Law & WIP Limits (Flow Metrics)

1. กายวิภาคของแผนภูมิการไหลสะสม (CFD)

  • แกน X: เส้นเวลา แกน Y: จำนวนงานสะสม
  • แถบล่าง Done: งานที่ปิดสมบูรณ์แล้ว แถบกลาง Code Review / QA: ด่านตรวจ PR/QA แถบบน In Progress: งานกำลังลงมือทำ (To Do → In Progress → Review → Done)
  • สภาวะปกติ (Healthy Flow): แถบสีทุกชั้นกว้างสม่ำเสมอ ขนานกัน ขยับขึ้นราบเรียบ ไร้จุดอุดตัน
  • สภาวะคอขวด (Bottleneck ): แถบชั้น Code Review / QA บวมกว้างผิดปกติ — งานติดค้างรอ Tech Lead ตรวจ PR นานเกินไป

2. กฎการหาจุดคอขวด + กฎของลิตเติล + WIP Limits

  • กฎของลิตเติล (Little's Law): ยิ่งปล่อยให้งานสะสมในช่อง Review สูง ระยะเวลาที่งานจะเสร็จยิ่งนานขึ้น
  • WIP Limits บน Jira: จำกัดช่อง Code Review 3 ใบ หากเต็มโควต้า สมาชิกทุกคนต้องหยุดเขียนโค้ดใหม่แล้วมาช่วยกันรีวิวโค้ดที่ค้างให้เสร็จก่อน

6. เงื่อนไข Freeze & แบบฟอร์มตรวจรับ UAT

1. เงื่อนไขการแช่แข็ง (Freeze Terms)

  1. ล็อก Scope ที่ 29 สตอรีพอยต์ (แผนเดิม 20 + CR-01 5 + CR-02 4) ห้ามเพิ่มฟีเจอร์ใหม่หรือเปลี่ยนข้อกำหนดในรีลีสปัจจุบัน
  2. สัปดาห์ที่ 12 (Sprint 3) เป็นช่วงเวลาแห่งความนิ่ง มุ่งเฉพาะ UAT และเตรียม Release Notes เท่านั้น
  3. งานที่อนุญาตช่วง Freeze: แก้บั๊กวิกฤต อุดช่องโหว่ Bandit/Flake8 เขียน Unit Test เพิ่ม (ตาม Code Freeze ISO 12207)
  4. ห้าม: แตก Branch ฟีเจอร์ใหม่ ปรับ UI รับ CR ตัวใหม่ — แก้โค้ดนาทีสุดท้ายคือสาเหตุอันดับ 1 ที่ทำให้ระบบพังวันส่งมอบ

2. แบบฟอร์มตรวจรับ UAT (Acceptance Protocol)

  • System Testing (ENGSE225): ทดสอบเชิงเทคนิคว่าโค้ดทำงานถูกต้องตามสเปก — รัน PyTest Full Suite 100% Pass สแกนช่องโหว่
  • UAT Testing (ENGSE202): ทดสอบความพึงพอใจการใช้งานจริง — ตรวจความถูกต้องของข้อมูลรายงาน CSV
UAT ID สถานการณ์ทดสอบ เกณฑ์ตัดสิน สถานะ
UAT-01 เพิ่มสินค้าใหม่พร้อม Barcode และ Reorder Point บันทึกสำเร็จ ไร้ Crash Passed
UAT-02 ตัดสต็อกจนต่ำกว่าเกณฑ์ ตรวจการแจ้งเตือน ขึ้น Alert ชัดเจน Passed
UAT-03 ส่งออก CSV เปิดตรวจใน Excel Header/Data ถูกต้อง Passed

โครงแบบฟอร์ม: ฟีเจอร์ → ขั้นตอน → ผลที่คาดหวัง → ผ่าน/ไม่ผ่าน → ลายเซ็น

7. Entry Criteria, การเจรจา & กระทบยอดงบ

3. เกณฑ์เข้า UAT (Entry Criteria)

  • งาน 27/29 พอยต์สถานะ Done สาธิตได้ (CR-01 ครบ 100% CR-02 เหลือ 2 pts เป็นช่องว่างที่ทราบแล้ว)
  • ผ่าน Hardening: Atomic Writes, ไม่มี except แบบเปลือย, ลบ Dead Code แล้ว
  • รัน Flake8 + Bandit ล้างข้อที่พบหมด (แปะผลจริงในบันทึกปล่อยรีลีส)
  • ชุดทดสอบผ่านทั้งหมด เตรียมแบบฟอร์ม UAT แล้ว

4. ขั้นตอนการเจรจา → แบ็กล็อก v3.0

  1. โชว์ Burnup Chart ยืนยันส่งมอบ CR-01/CR-02 (27/29 Points, 93%)
  2. ชี้แจงความเสี่ยงเพิ่มฟังก์ชันใหม่โค้งสุดท้าย (High Anxiety Period)
  3. ยื่น Scope Freeze Agreement ให้อาจารย์ (Sponsor) ลงนามยืนยันไม่มีฟังก์ชันใหม่สัปดาห์ที่ 12
  4. ไอเดียใหม่ → Future Backlog (v3.0) ไม่แตะสปรินต์ปัจจุบัน ประเมินพอยต์ใหม่ วาง Baselines ใหม่
  5. Freeze มีผลจนกว่าจะลงนาม UAT ยกเลิกได้เมื่อทีม + อาจารย์ตกลงเป็นลายลักษณ์อักษรเท่านั้น
