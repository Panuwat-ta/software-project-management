## สคริปต์พูดประกอบสไลด์

### 1. วิวัฒนาการระบบจัดการสินค้าคงคลัง

“สวัสดีครับ วันนี้กลุ่มของเราจะนำเสนอพัฒนาการของระบบจัดการสินค้าคงคลัง ตั้งแต่โปรแกรม CLI รุ่นแรกที่เก็บข้อมูลในไฟล์ JSON จนถึงระบบที่ใช้ SQLite และโปรแกรม Desktop UI เราทำงานต่อเนื่อง 5 Sprint รวม 95 Story Points โดยตรวจสอบผลด้วยชุดทดสอบหลักและชุด regression รวม 21 และ 25 เคสตามลำดับ ตลอดการนำเสนอจะเห็นว่าทีมค่อย ๆ แก้ปัญหาทั้งด้านโครงสร้างข้อมูล การออกแบบ และการใช้งาน ไม่ได้เปลี่ยนแค่หน้าตาของโปรแกรมครับ”

### 2. ทีม เป้าหมาย และขอบเขต

“โครงการนี้แบ่งความรับผิดชอบตามบทบาทที่ช่วยกันส่งมอบงาน ภานุวัฒน์รับผิดชอบภาพรวมโครงการและพัฒนาระบบ เอกพันธ์ดูแลกรณีทดสอบ regression และ edge cases ส่วนณฐภาพดูแลสถาปัตยกรรม การทบทวนโค้ด และ quality gate เป้าหมายหลักคือเพิ่มเสถียรภาพ แยกส่วนติดต่อผู้ใช้ออกจาก business logic และต่อยอดข้อมูลจาก JSON ไปสู่ SQLite พร้อมฟังก์ชันสมาชิก Checkout และ Desktop Program ขอบเขตในวันนี้จึงครอบคลุมตั้งแต่ Sprint 1 ถึง Sprint 5 ครับ”

### 3. เส้นทาง Sprint 1 → Sprint 5

“แผนงานแบ่งเป็น 5 Sprint โดย Sprint 1 วางฐาน 15 SP, Sprint 2 ออกแบบและจัดทำ cost baseline 13 SP, Sprint 3 ควบคุมการเปลี่ยนแปลง 16 SP, Sprint 4 ทำ UAT และ Release 5 SP และ Sprint 5 พัฒนาระบบ SQLite กับ Desktop Program 46 SP รวมเป็น 95 SP รายงานระบุว่าทั้ง 5 Sprint ปิดแล้ว และมีหลักฐานประกอบให้ตรวจสอบ เป้าหมายของสไลด์นี้คือทำให้เห็นลำดับของงาน ตั้งแต่การทำความเข้าใจปัญหาไปจนถึงผลิตภัณฑ์ที่นำมาสาธิตครับ”

### 4. จุดเริ่มต้น: ระบบเดิมแบบ Monolithic

“ก่อนเริ่มปรับปรุง ระบบทำงานผ่าน CLI มี 5 เมนูและเก็บข้อมูลใน `data.json` จุดสำคัญคือฟังก์ชัน `main()` ทำทั้งส่วนแสดงผล ตรรกะการทำงาน และการบันทึกข้อมูล ข้อมูลบางส่วนยังอยู่ใน global variable และ validation ยังไม่ครอบคลุม เมื่อเขียนทับไฟล์โดยตรง ความผิดพลาดระหว่างบันทึกอาจทำให้ข้อมูลเสียได้ ส่วนค่าความซับซ้อนของ `main()` อยู่ที่ CC 14 ระดับ C จึงใช้ข้อมูลนี้เป็น baseline เพื่อชี้ว่าควรแยกส่วนและลดความเสี่ยงตรงไหนครับ”

### 5. Hotspot → Refactor → Automated Test

“ทีมเริ่มแก้จาก hotspot ที่รวมหลายหน้าที่ไว้ด้วยกัน โดยแยกเป็น `Product` สำหรับข้อมูลสินค้า, `InventoryManager` สำหรับ business logic และ validation และ `InventoryCLI` สำหรับส่วนติดต่อผู้ใช้ การบันทึกแบบ Atomic Save ช่วยลดโอกาสที่ไฟล์จะค้างอยู่ในสภาพเขียนไม่ครบ และยังรองรับ key เก่าบางรูปแบบเพื่อรักษาความเข้ากันได้ หลัง refactor ชุดทดสอบ PyTest ผ่าน 5 จาก 5 เคส และงาน SPM-6 ถึง SPM-10 รวม 15 SP เสร็จตามรายงานครับ”

### 6. To-Be Architecture + Quality Gate

“ใน Sprint 2 ทีมกำหนดสถาปัตยกรรมก่อนเริ่มลงมือ เพื่อให้เปลี่ยนส่วนแสดงผลหรือฐานข้อมูลในอนาคตได้โดยไม่ต้องย้าย business rule ทั้งหมด Presentation ติดต่อ Service, Service จัดการ validation และ Checkout, Repository ซ่อนรายละเอียด CRUD และ SQL แล้วจึงบันทึกผ่าน SQLite การแบ่งชั้นนี้ทำให้แต่ละส่วนมีหน้าที่ชัดเจน นอกจากนี้ยังตั้ง cost baseline ที่ 18,823 บาท กำลังการทำงาน 36 ชั่วโมงต่อ Sprint เป้าหมาย coverage อย่างน้อย 85 เปอร์เซ็นต์ และเป้าหมาย CC ไม่เกิน 8 ตัวเลขเหล่านี้เป็น baseline และเกณฑ์ที่วางไว้สำหรับติดตามคุณภาพและต้นทุนครับ”

### 7. Change Control ที่ตรวจสอบย้อนหลังได้

“เมื่อมีงานเพิ่ม ทีมใช้กระบวนการ Change Control เพื่อประเมินผลกระทบก่อนแก้ baseline เริ่มจาก Submit, วิเคราะห์ Impact, ให้ CCB Review แล้วจึงปรับ Baseline ตัวอย่างคือ CR-01 เพิ่ม Barcode และ Reorder Point โดยประเมินผลกระทบ 8 ชั่วโมง, CR-02 เพิ่ม CSV Export แบบ fast-track ใช้เวลา 4.5 ชั่วโมง คิดเป็น 1,350 บาทและเบิกจาก reserve ส่วน BUG-101 เกิดจากข้อมูลเดิมไม่มี key `barcode` จึงเพิ่ม fallback และ regression test ก่อน Freeze มีงานเสร็จ 27 จาก 29 SP และกำหนด WIP limit ที่ 3 เพื่อควบคุมงานที่อยู่ระหว่าง review ครับ”

### 8. UAT และ Release v2.0

“ก่อนปล่อย v2.0 ทีมตรวจทั้ง regression และ acceptance scenario ผล regression ผ่าน 25 จาก 25 เคส และ UAT ผ่าน 3 จาก 3 scenario ได้แก่ เพิ่มสินค้าและกำหนด Reorder Point, ตัดสต็อกแล้วตรวจ low-stock และส่งออก CSV ตัวชี้วัดในสรุประบุ SPI 1.00 และ CV ลบ 575 บาท เอกสาร release รวม Changelog, Final EVM และ Technical Gate ไว้ด้วย อย่างไรก็ตาม Formal UAT Sign-off ยังรอลายเซ็นผู้รับรอง จึงควรแยกผลทดสอบทางเทคนิคที่ผ่านแล้วออกจากการอนุมัติรับรองอย่างเป็นทางการครับ”

### 9. จาก v1.0 ถึง v4.0 Desktop

“สไลด์นี้รวบรวมการวิวัฒนาการของระบบเป็น 4 ช่วง v1.0 เป็น CLI แบบ Monolithic ใช้ JSON; v2.0 แยกเป็น OOP 3 คลาสและเพิ่ม Atomic Save, validation, Barcode, Reorder Point และ CSV; v3.0 ย้ายข้อมูลไป SQLite และเพิ่ม Repository, Strategy, สมาชิก 4 ระดับ และ Checkout; ส่วน v4.0 Desktop เพิ่ม GTK4 UI ที่นำ domain เดิมกลับมาใช้กับหน้า Dashboard, Products, Members และ Checkout แนวทางนี้ช่วยให้เพิ่มช่องทางใช้งานโดยไม่ต้องเขียนกฎทางธุรกิจชุดใหม่ครับ”

### 10. Data/Domain Architecture

“งาน Sprint 5 แบ่งเป็น Data/Domain 17 SP และ Desktop UI 29 SP รวม 46 SP ฝั่ง CLI และ Desktop เรียกใช้ `app.py` และ `program.py` ผ่าน `CheckoutService` จากนั้นใช้ `InventoryRepository` และ Strategy ก่อนบันทึกข้อมูลใน SQLite ดังนั้น UI ไม่ได้เขียน SQL เองหรือคำนวณส่วนลดซ้ำ งาน migration มีการตรวจสอบข้อมูลหลังย้ายตามรายงาน สถาปัตยกรรมนี้ทำให้การเปลี่ยนหน้าจอไม่กระทบแหล่งที่มาของกฎทางธุรกิจ และช่วยให้ทดสอบ logic แยกจาก UI ได้ครับ”

### 11. Member Strategy + Checkout

“ระบบสมาชิกมี 4 ระดับ ได้แก่ Regular ไม่มีส่วนลด, Silver 5 เปอร์เซ็นต์, Gold 10 เปอร์เซ็นต์ และ Platinum 15 เปอร์เซ็นต์ การคำนวณส่วนลดถูกรวมไว้ใน `CheckoutService` เพื่อให้มีแหล่งคำนวณเดียว ตัวอย่างในสไลด์คือสมาชิก Gold ซื้อสินค้า 2 ชิ้น ชิ้นละ 500 บาท รวมก่อนลด 1,000 บาท ได้ส่วนลด 100 บาท จึงชำระ 900 บาท ส่วน Guest ชำระราคาเต็ม ใบเสร็จยังแสดงยอดและสต็อกคงเหลือด้วยครับ”

### 12. Epic SPM-28: CLI → Desktop Program UI

“หลักฐาน Jira แสดง Epic SPM-28 และ Stories SPM-29 ถึง SPM-32 สำหรับการเปลี่ยนจากขอบเขต Web มาเป็น Desktop Program UI ทีมปรับรายละเอียดของงานให้ตรงกับสิ่งส่งมอบจริง โดย SPM-29 วาง GTK4 foundation และ reuse domain, SPM-30 ทำ Dashboard กับ Products, SPM-31 ทำ Members กับ Checkout และ SPM-32 ทำ responsive hardening กับ quality gate ตามข้อมูลในสไลด์ Story Points, parent และสถานะ Done ยังคงเดิม การเชื่อม Jira กับตัวส่งมอบทำให้ตรวจย้อนกลับจากแผนงานไปยังหลักฐานได้ครับ”

### 13. Dashboard

“หน้านี้เป็น Dashboard ของ Desktop Program ที่สรุปสถานะคลังเพื่อให้ผู้ใช้เห็นสิ่งที่ควรจัดการก่อน โดยมีจำนวนประเภทสินค้า มูลค่าคงคลัง และรายการ low-stock พร้อมสถานะ SQLite และเวลาอัปเดตล่าสุด รูปแบบหน้าจอปรับตามขนาดหน้าต่าง เพื่อให้ยังใช้งานได้เมื่อพื้นที่แสดงผลเปลี่ยน Dashboard จึงเป็นจุดเริ่มต้นสำหรับมองภาพรวม ก่อนเข้าไปจัดการสินค้าหรือทำ Checkout ครับ”

### 14. Products

“หน้า Products รวมงานจัดการสินค้าประจำวัน ผู้ใช้เพิ่มหรือแก้ไขข้อมูล ค้นหาด้วยรหัส ชื่อ หรือหมวดหมู่ ตัดสต็อก ลบรายการ และส่งออก CSV ได้ ป้าย LOW และ OK ช่วยแยกสินค้าที่ถึงจุดสั่งซื้อซ้ำออกจากรายการปกติ การแสดง action ต่อแถวช่วยให้จัดการรายการได้จากตารางเดียว ขณะที่ข้อมูลจริงยังผ่าน Repository และ domain layer เดิมครับ”

### 15. Members

“หน้า Members ใช้เพิ่ม แก้ไข และลบสมาชิก พร้อมเลือกหนึ่งในสี่ระดับ Regular, Silver, Gold หรือ Platinum ป้ายส่วนลดทำให้เห็น policy ของสมาชิกได้ทันทีระหว่างจัดการข้อมูล เมื่อทำ Checkout การคิดส่วนลดยังคงเรียกกฎชุดเดียวจาก `CheckoutService` แทนการคำนวณซ้ำบนหน้าจอ ช่วยให้ผลที่ผู้ใช้เห็นสอดคล้องกับผลที่ระบบบันทึกครับ”

### 16. Checkout

“หน้า Checkout รองรับทั้ง Guest และสมาชิก ผู้ใช้เลือกรายการสินค้าและจำนวน จากนั้นระบบตรวจสต็อก คิดส่วนลดตาม tier และแสดงใบเสร็จ ยอดสุทธิถูกเน้นให้เห็นชัด พร้อมแสดงยอดก่อนลด ส่วนลด และจำนวนสินค้าคงเหลือ การใช้ `CheckoutService` ทำให้ UI ทำหน้าที่รับข้อมูลและแสดงผล ส่วนกฎการขายและการคิดเงินอยู่ใน domain layer ครับ”

### 17. สถานะสุดท้ายของโครงการ

“ผล quality gate ในสไลด์นี้ประกอบด้วยชุดหลัก 21 จาก 21 เคส ซึ่งรวม Desktop integration 7 เคส และ regression ของ v2.0 อีก 25 จาก 25 เคส การตรวจ Flake8 และ Bandit รายงานปัญหาเป็นศูนย์ integration tests ครอบคลุม responsive breakpoints, seed data, dashboard metrics, สถานะ LOW/OK, member checkout, ใบเสร็จ และ CSV ส่วน regression ตรวจพฤติกรรม baseline รวมถึง CR-01, CR-02 และ BUG-101 ตัวเลขนี้ยืนยันผลของชุดตรวจที่ระบุ แต่ Formal UAT Sign-off ยังเป็นขั้นตอนแยกที่รอดำเนินการครับ”

### 18. มุมมองรวม 5 Sprint

“เมื่อมองโครงการทั้ง 5 Sprint จะเห็นมิติการบริหารที่เชื่อมกันด้วยหลักฐานเดียวกัน Scope รวม 95 SP และทุก Sprint ปิดแล้ว; Cost ติดตามจาก baseline 18,823 บาทไปยัง CV ลบ 575 บาท; Quality มี DoR/DoD, ISO gate และ automated tests; Change ใช้ CR-01, CR-02 และ BUG-101; Release ครอบคลุม v2.0 gate และ Desktop candidate ส่วน Evidence เชื่อมรายงาน Jira ผลทดสอบ และภาพหน้าจอเข้าด้วยกัน สไลด์นี้จึงสรุปทั้งงานผลิตซอฟต์แวร์และกระบวนการควบคุมโครงการครับ”

### 19. Project Outcome

“ผลลัพธ์ของโครงการคือการเปลี่ยนจาก CLI แบบ Monolithic ไปสู่ระบบที่แยกชั้น ใช้ SQLite และ transaction เพิ่ม Member Strategy กับ Checkout และเปิดใช้งานผ่าน Desktop UI ที่ reuse domain เดิม หลักฐานที่นำเสนอประกอบด้วยผลทดสอบ 21 เคสหลักและ 25 เคส regression รวมทั้งผล Flake8 และ Bandit ที่เป็นศูนย์ งานต่อไปที่เสนอคือทำ executable หรือ installer, ปิด Formal UAT Sign-off, เพิ่ม Role/Login หากมีการขยายขอบเขต และพิจารณา PostgreSQL เมื่อต้องรองรับหลายผู้ใช้ ขอบคุณครับ”

## หมายเหตุสำหรับผู้นำเสนอ

- ตัวเลขผลทดสอบ คุณภาพ ต้นทุน และสถานะ Jira ในสคริปต์นี้อ้างตามหลักฐานที่ระบุบนสไลด์และรายงานของแต่ละ Sprint
- เมื่อนำเสนอผล UAT ให้แจ้งด้วยว่า scenario ผ่านทางเทคนิคแล้ว แต่ Formal UAT Sign-off ยังรอลายเซ็นผู้รับรอง
- ชื่อบุคคล ตัวเลข Story Points และสถานะ Jira ควรยึดตามหลักฐานฉบับที่ใช้ส่งงาน หากมีการปรับข้อมูลโครงการภายหลัง
