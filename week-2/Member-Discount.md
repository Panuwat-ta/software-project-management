# ระบบสมาชิกลดราคา

หากลูกค้าต้องการเพิ่มฟีเจอร์ระบบสมาชิกลดราคา (Member Discount) และต้องการให้ระบบนี้เสถียรไม่ล่มง่าย ทีมเราจะวางแผนการทำงาน (Scope) และประเมินความเสี่ยงอย่างไร บนฐานโค้ดตัวนี้

---

## 1. การวางแผนการทำงาน (Scope)

จากฐานโค้ดปัจจุบัน ซึ่งใช้ Global Variable และเก็บข้อมูลในรูปแบบไฟล์ JSON โปรแกรมจะยังไม่มีความเสถียรพอที่จะรองรับฟีเจอร์ที่ซับซ้อนขึ้น การวางแผนจึงต้องเริ่มจากการปรับปรุงโครงสร้างเดิมก่อน ดังนี้:

**Phase 1: ปรับปรุงโครงสร้างพื้นฐานและฐานข้อมูล (Refactoring & Database Migration)**
- เปลี่ยนจากการจัดเก็บข้อมูลแบบไฟล์ JSON มาใช้ฐานข้อมูล **SQLite** เพื่อความปลอดภัยและรองรับการทำธุรกรรม (ACID Properties)
- Refactor โค้ดจากการใช้ตัวแปรระดับ Global (`x`) ให้เป็นรูปแบบ **Object-Oriented Programming (OOP)** หรือใช้ **MVC Pattern** แยกส่วน Data Access ออกจาก Business Logic

**Phase 2: พัฒนาระบบจัดการสมาชิก (Membership Management)**
- **TASK-11:** ออกแบบฐานข้อมูล (Schema) สำหรับข้อมูลสมาชิก และกำหนดตรรกะระดับส่วนลด (เช่น Regular 0%, Silver 5%, Gold 10%, Platinum 15%)
- **TASK-13:** สร้างระบบจัดการข้อมูลสมาชิกแบบ CRUD (เพิ่ม ดู แก้ไข ลบ ข้อมูลสมาชิก)

**Phase 3: นำระบบไปผสานในขั้นตอนการขาย (Integration)**
- **TASK-14:** นำตรรกะส่วนลดเข้าไปใส่ในขั้นตอนการตัดสต็อกสินค้า โดยคำนวณส่วนลดจากรหัสสมาชิกให้ถูกต้อง 

**Phase 4: ระบบทดสอบ (Automated Testing)**
- **TASK-15:** เขียน Unit Test และ Integration Test สำหรับคลาสต่างๆ และฐานข้อมูล เพื่อให้มั่นใจว่าการคำนวณและดึงข้อมูลจะไม่ทำให้ระบบแครช

## 2. การประเมินความเสี่ยง (Risk Assessment) และวิธีรับมือ

เมื่ออ้างอิงจากฐานโค้ดเดิม และฟีเจอร์ที่ต้องเพิ่ม มีความเสี่ยงที่ทีมต้องประเมินและป้องกันดังนี้:

1. **ความเสี่ยงไฟล์ข้อมูลพัง (Data Corruption Risk)**
   - **ปัญหา:** ปัจจุบันระบบใช้ `json.dump` เขียนทับไฟล์ทั้งหมดในครั้งเดียว หากโปรแกรมหรือคอมพิวเตอร์ดับระหว่างทำงาน ไฟล์ `data.json` จะพังทันที ข้อมูลทั้งหมดสูญหาย
   - **การรับมือ:** ย้ายไปใช้ **SQLite** ซึ่งรองรับระบบ Transaction (Begin, Commit, Rollback) สามารถป้องกันข้อมูลเสียหายเมื่อระบบล่มกลางคันได้

2. **ความเสี่ยงตัวแปรชนกัน (Global State Conflict Risk)**
   - **ปัญหา:** โปรแกรมปัจจุบันใช้ตัวแปร `global x` ในการเก็บสถานะ หากมีการเพิ่มระบบ Member เข้ามาและจัดการด้วย Global อีก จะทำให้ข้อมูลตีกันและบั๊กตามแก้ยากมาก
   - **การรับมือ:** ปรับปรุงโค้ดให้เป็น OOP และส่งผ่านตัวแปรแบบพารามิเตอร์ (Parameter/Return) แทนการใช้ Global

3. **ความเสี่ยงจากข้อมูลเข้าที่ไม่ถูกต้อง (Input Mismatch & App Crash)**
   - **ปัญหา:** การรับค่า Input ในปัจจุบัน หากผู้ใช้กรอกผิดประเภท เช่น ใส่ตัวอักษรในช่องจำนวนสินค้า ระบบจะเกิด Exception (ValueError) และโปรแกรมหยุดทำงาน (Crash) ทันที
   - **การรับมือ:** สร้าง Input Validator มาครอบและใช้ `try-except` ในการจัดการ Error เพื่อให้ระบบแค่แจ้งเตือนแล้วทำงานต่อได้ แทนที่จะล่ม

4. **ความเสี่ยงการโจมตีหรือข้อผิดพลาดในคำสั่งฐานข้อมูล (SQL Injection)**
   - **ปัญหา:** ในการย้ายไปใช้ SQLite หากเขียนคำสั่ง SQL โดยการต่อ String (`"SELECT * FROM members WHERE id = " + id`) อาจทำให้เกิดบั๊กจากคำสั่งผิดรูปแบบหรือโดนโจมตี 
   - **การรับมือ:** ต้องบังคับใช้ **Parameterized Query** (เช่น `cursor.execute(query, (id,))`) เท่านั้นในการเข้าถึงข้อมูล
