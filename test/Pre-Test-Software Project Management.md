## ข้อที่ 1: Brownfield, Project Charter และ WBS

*สัปดาห์ที่ 1–2*

### 1.1 Scope Management

การจัดการขอบเขตของ Brownfield Project ต่างจาก Greenfield Project อย่างไร และเหตุใดจึงมักเกิด Hidden Scope?

#### คำตอบ 1.1

- **Brownfield:** ต้องเพิ่มหรือแก้บนระบบที่ใช้งานอยู่ จึงต้องคุมความเข้ากันได้, Technical Debt, dependency และผลกระทบข้างเคียงต่อฟังก์ชันเดิม ส่วน **Greenfield** เริ่มจากศูนย์ จึงเน้นความไม่แน่นอนของความต้องการและการออกแบบใหม่มากกว่า
- **Hidden Scope:** เกิดเมื่อประเมินเฉพาะฟีเจอร์ใหม่ แต่ยังไม่เห็นงานทำความเข้าใจโค้ดเดิม, impact analysis, Refactoring และ regression testing เพราะเอกสาร/ความรู้เดิมไม่ครบ จึงพบบั๊กหรือ dependency ซ่อนอยู่เมื่อเริ่มแกะระบบ

### 1.2 Work Breakdown Structure (WBS)

WBS คืออะไร? จงเขียน WBS อย่างน้อย 3 ระดับสำหรับ “การปรับปรุงระบบคลังสินค้า v1.1 เพื่อเพิ่มระบบสมาชิกลดราคา” โดยครอบคลุมงานเทคนิคและงานบริหารจัดการ

#### คำตอบ 1.2

- **WBS** คือการสลายโครงการให้เป็นโครงสร้างลำดับชั้นของ Work Package ที่จัดการ วัดผล ประเมินเวลา/ต้นทุน และมอบหมายผู้รับผิดชอบได้
- **โครงสร้าง WBS:**
  1. การปรับปรุงระบบคลังสินค้า v1.1
    1.1 การบริหารและกำกับโครงการ
      1.1.1 จัดทำ Project Charter, WBS, RACI และ Risk Register
      1.1.2 วางแผนงบประมาณ/กำหนดการ และติดตามบน Jira/Trello
    1.2 วิเคราะห์และเตรียมระบบเดิม
      1.2.1 ทำ Static Analysis, DFD และ Impact Analysis
      1.2.2 ตั้ง Git repository, baseline, branching และ Branch Protection
    1.3 ลดความเสี่ยงของโค้ดเดิม
      1.3.1 เขียน Automated Regression Test สำหรับลดสต็อกและยอดรวม
      1.3.2 Refactor แยก `main()` และกำจัด/ห่อหุ้ม Global State
    1.4 พัฒนาฟีเจอร์สมาชิก
      1.4.1 ออกแบบข้อมูล Member ID และกฎ/เปอร์เซ็นต์ส่วนลด
      1.4.2 พัฒนาและรวมฟังก์ชันคำนวณราคาสุทธิหลังหักส่วนลด
    1.5 ทดสอบและส่งมอบ
      1.5.1 ทำ code review, CI และทดสอบการยอมรับ
      1.5.2 อัปเดตเอกสาร/Change Log และส่งมอบ

## ข้อที่ 2: การบริหารความเสี่ยงทางเทคนิค และ Risk Matrix

*สัปดาห์ที่ 2*

### 2.1 ความไม่แน่นอนในโครงการ Legacy

จงอธิบายความแตกต่างระหว่าง Known-Unknowns และ Unknown-Unknowns ในโครงการ Legacy และเหตุผลที่ Brownfield ต้องเผื่อเวลา 1.5–2.0 เท่า

#### คำตอบ 2.1

- **Known-Unknowns:** รู้ว่ามีเรื่องไม่แน่นอนและระบุไว้ใน Risk Register ได้ เช่น ต้องเชื่อมฐานข้อมูล/API ที่ยังไม่เคยศึกษาหรือผลกระทบจากจุดเสี่ยงที่พบ จึงวางแผนลดความเสี่ยงและกัน Contingency Reserve ได้
- **Unknown-Unknowns:** สิ่งที่ยังไม่รู้ว่ามีอยู่ เช่น แกะโค้ดเก่าแล้วพบ dependency หรือบั๊กซ้อนที่ไม่มีเอกสาร จึงมักต้องใช้ Management Reserve ซึ่ง Sponsor อนุมัติ
- **เหตุที่ใช้ Buffer 1.5–2.0 เท่า:** เวลาใน Brownfield ไม่ได้มีเพียงเวลาเขียนโค้ด แต่มีค่าแกะระบบ แก้ผลกระทบข้างเคียง และทดสอบ regression จากหนี้เทคนิค/ความไม่รู้ที่ซ่อนอยู่ จึงต้องเผื่อเวลาให้แผนยังควบคุมได้

### 2.2 Mitigation Plan

หากการแก้ฟังก์ชันลดสต็อกอาจทำให้การคำนวณมูลค่ารวมผิดพลาด (High Risk) จงเสนอแผนบรรเทาความเสี่ยงเชิงรุก 2 ข้อ

#### คำตอบ 2.2

1. **สร้าง safety net ก่อนแก้:** เขียน Automated Unit/Regression Test ให้ครอบคลุมการลดสต็อกและการคำนวณมูลค่ารวม แล้วบังคับให้รันใน CI ทุก PR; หากยอดรวมเปลี่ยนโดยไม่ตั้งใจ ระบบจะตรวจพบก่อน merge
2. **ลดจุดพึ่งพาร่วม:** ทำ Refactoring แยก scope/encapsulate `global x` และแยกความรับผิดชอบของการปรับสต็อกออกจากการคำนวณมูลค่า พร้อมทำ PR และ code review เป็นงานย่อยใน WBS ก่อนแก้ฟีเจอร์หลัก

## ข้อที่ 3: RACI Matrix, Communication Management และ Agile Sync

*สัปดาห์ที่ 3 และ 6*

### 3.1 RACI Matrix

RACI Matrix คืออะไร? จงอธิบาย R, A, C, I และเหตุผลที่แต่ละกิจกรรมต้องมี Accountable (A) เพียงคนเดียว

#### คำตอบ 3.1

- **RACI Matrix** ระบุบทบาทในทีม:
  - **R (Responsible):** ผู้ปฏิบัติงาน
  - **A (Accountable):** ผู้รับผิดชอบความสำเร็จ (มีอำนาจตัดสินใจเด็ดขาด)
  - **C (Consulted):** ผู้ให้คำปรึกษา
  - **I (Informed):** ผู้รับทราบข้อมูล
- **เหตุที่ต้องมี A เพียงคนเดียว:** เพื่อป้องกันการโยนความรับผิดชอบหรือการเกียร์ว่าง เมื่อมีปัญหาจะได้รับรู้ว่าใครเป็นผู้ตัดสินใจขั้นสุดท้าย

### 3.2 การสื่อสารในทีม

จงอธิบายสูตร `c = n(n-1)/2` ว่าทำไมการสื่อสารไร้ระเบียบจึงเกิด Communication Overhead Cost และเสนอการใช้ Communication Matrix กับ Daily Standup 15 นาทีเพื่อแก้ปัญหา

#### คำตอบ 3.2

- สูตร `c = n(n-1)/2` คือจำนวนช่องทางสื่อสารแบบจับคู่ของคน `n` คน เช่น ทีม 5 คนมี 10 ช่องทาง จึงเพิ่มแบบกำลังสองเมื่อจำนวนคนเพิ่ม
- **Communication Overhead:** หากไม่มีข้อตกลง คนอาจถาม/รายงานซ้ำหลายช่องทาง ข้อมูลไม่ตรงกัน หรือประชุมยาวจนเวลาพัฒนาลดลง และ blocker ถูกพบช้า
- **แนวทางแก้ไข:**
  - **Communication Matrix:** กำหนดหัวข้อ, ช่องทาง, ความถี่, ผู้รับ และผู้รับผิดชอบ เช่น บันทึกงานใน Jira, รายงาน Sponsor รายสัปดาห์ และคุย blocker ทาง Discord/Slack เพื่อให้ข้อมูลถึงคนที่ต้องใช้จริง
  - **Daily Standup:** ประชุมไม่เกิน 15 นาทีตอบว่าเมื่อวานทำอะไร วันนี้ทำอะไร และมี blocker หรือไม่; ประเด็นเชิงลึกแยกคุยหลังประชุม จึงซิงค์ทีมได้โดยไม่กลายเป็นการประชุมยาว

## ข้อที่ 4: การประมาณการต้นทุน และ Cost Baselining

*สัปดาห์ที่ 5 และ 7*

### 4.1 Cost Estimation

จงเปรียบเทียบ Analogous Estimating กับ Bottom-up Estimating และอธิบายว่าเหตุใด Bottom-up จึงแม่นยำกว่าในงาน Refactoring

#### คำตอบ 4.1

- **Analogous Estimating:** ใช้ข้อมูลและขนาดโครงการในอดีตที่คล้ายกันมาเทียบเพื่อประมาณแบบภาพรวม รวดเร็ว เหมาะระยะแรก แต่คลาดเคลื่อนง่ายหากหนี้เทคนิคของระบบเก่าไม่เหมือนกัน
- **Bottom-up Estimating:** ประเมินเวลา/ต้นทุนของ Work Package ย่อยที่สุดใน WBS แล้วรวมขึ้นเป็นงบ ใช้เวลาวิเคราะห์มากกว่า แต่ละเอียดกว่า
- **เหตุที่แม่นยำกว่า:** สามารถแปลงผลวิเคราะห์ ISO 25010 เป็นงานเฉพาะ เช่น แยก `main()`, เขียน PyTest, จัดการ Global State และกำหนด role/Man-hours ของแต่ละงาน จึงสะท้อนความยากและความเสี่ยงที่แตกต่างกันจริง

### 4.2 Total Estimated Project Cost และ Cost Variance

จงอธิบาย Direct Labor Cost, Infrastructure/Tooling Cost และ Contingency Reserve พร้อมเกณฑ์ Cost Variance (เขียว เหลือง แดง) และวิธีที่ PM ควบคุมเมื่อเกินงบ

#### คำตอบ 4.2

- **Direct Labor Cost:** ชั่วโมงทำงานตาม WBS/RACI คูณอัตราค่าแรงของ PM, Tech Lead, Developer และ QA
- **Infrastructure/Tooling Cost:** ค่า cloud/server, database, CI/CD compute และ license เครื่องมือ เช่น Jira, GitHub หรือเครื่องมือวิเคราะห์โค้ด
- **Contingency Reserve:** งบสำรองสำหรับความเสี่ยงที่ระบุได้ (known-unknowns) ตาม Risk Register; ต่างจาก Management Reserve สำหรับเหตุการณ์ที่คาดไม่ถึงซึ่งต้องขอ Sponsor อนุมัติ
- **Cost Variance Thresholds:**
  - **สีเขียว (Normal ≤ 5%):** อยู่ในเกณฑ์ ควบคุมและติดตามตามปกติ
  - **สีเหลือง (Warning > 5%–10%):** PM วิเคราะห์สาเหตุ ทำรายงานชี้แจง และปรับแผน Man-hours/การจัดสรรงานก่อนบานปลาย
  - **สีแดง (Critical > 10%):** ดำเนินแผนแก้ไขทันที เช่น ใช้ Contingency Reserve สำหรับความเสี่ยงที่ระบุไว้ หรือเจรจาตัด/เลื่อน scope; หากเป็นเหตุเหนือ Risk Register จึงยื่น Sponsor ขอใช้ Management Reserve หรืออนุมัติเปลี่ยน baseline

## ข้อที่ 5: Quality Gates, DoD และ Phase Gate Review

*สัปดาห์ที่ 3, 6 และ 7*

### 5.1 Quality Gate, DoR และ DoD

Quality Gate บน Jira/Trello คืออะไร? DoR และ DoD ช่วยสกัดกั้นโค้ดไม่มีคุณภาพไม่ให้ถึงลูกค้าอย่างไร? จงยกตัวอย่าง DoD 3 ข้อ

#### คำตอบ 5.1

- **Quality Gate:** จุดควบคุมที่การ์ดงาน/ชิ้นงานต้องผ่านเกณฑ์ก่อนจึงขยับสถานะหรือข้ามเฟสได้ เช่น กักงานไว้ที่ Code Review/QA ก่อน Done
- **DoR:** ตรวจคุณภาพ “ก่อนเริ่ม” ว่า backlog พร้อมพัฒนาหรือไม่ เช่น คำอธิบายชัด มี estimate, assignee และความเสี่ยง
- **DoD:** ตรวจคุณภาพ “ก่อนเสร็จ” ว่างานผ่านเกณฑ์ทางเทคนิคและกระบวนการแล้ว DoR ลดการเริ่มงานผิดหรือคลุมเครือ ส่วน DoD ป้องกันโค้ดที่ยังไม่ตรวจ/ไม่ทดสอบไม่ให้ไปถึง `develop` และผู้ใช้
- **ตัวอย่าง DoD:**
  1. ผ่าน Peer Code Review และได้รับ approval อย่างน้อย 1 คน
  2. PyTest/Automated CI ผ่านไฟเขียว 100%
  3. PR ถูก merge เข้า `develop` แล้ว และบันทึก Log Time จริงใน Jira

### 5.2 Phase Gate Review (Tollgate)

Phase Gate Review คืออะไร? จงอธิบายบทบาทของ Project Manager และ Project Sponsor ในการ Sign-off Phase 2 เพื่ออนุญาตให้เริ่ม Sprint 1

#### คำตอบ 5.2

- **Phase Gate Review (Tollgate):** จุดกำกับดูแลหลังจบเฟสเพื่อประเมินหลักฐานและตัดสินใจ Go/No-Go; ใน Gate 2 ต้องพิสูจน์ว่า architecture, งบประมาณ, SCM/automation และ Sprint backlog พร้อมดำเนินการ
- **บทบาท Project Manager:** เป็นผู้นำเสนอและชี้แจงแผนบูรณาการ ได้แก่ scope/กำหนดการ, Cost Baseline, ความเสี่ยง, Quality Gate และความพร้อมของงาน Sprint 1
- **บทบาท Project Sponsor (อาจารย์/ลูกค้า):** ซักถาม ตรวจหลักฐาน และเป็นผู้มีอำนาจ Sign-off เมื่อเห็นว่าแผนยอมรับได้ การลงนามปิด Phase 2 อย่างเป็นทางการและอนุมัติ baseline จึงมอบสิทธิ์ให้ PM กด `Start Sprint 1`; หากไม่ผ่าน ทีมต้องแก้ช่องว่างก่อนเริ่มเขียนโค้ดจริง
