RACI Matrix คืออะไร?
เครื่องมือจัดระเบียบบทบาท: คือตารางแสดงความรับผิดชอบ (Responsibility Assignment Matrix - RAM) ที่ใช้จับคู่ระหว่าง "กิจกรรมในโครงการ" กับ "บทบาทหน้าที่ของสมาชิกในทีม" เพื่อไม่ให้เกิดความซ้ำซ้อนหรือช่องว่างในการทำงาน
 อ้างอิง: IEEE Std 1490-2011 (IEEE Guide for Adoption of PMBOK Guide Framework) 

Responsible (ผู้ลงมือทำ)
ผู้ที่ต้องรับผิดชอบทำงานชิ้นนั้นให้เสร็จสิ้น (ใน 1 กิจกรรมสามารถมี R ได้มากกว่า 1 คน)
Accountable (ผู้อนุมัติ/รับผิดชอบสูงสุด)
ผู้มีอำนาจตัดสินใจเด็ดขาดและเป็นคนเซ็นอนุมัติงาน **กฎเหล็ก: ใน 1 กิจกรรมต้องมี A เพียงคนเดียวเท่านั้น
Consulted (ที่ปรึกษา)
ผู้เชี่ยวชาญหรือผู้มีส่วนเกี่ยวข้องที่ต้องให้คำแนะนำ ข้อมูล หรือความเห็นก่อนที่งานจะเริ่มหรือเสร็จสิ้น
Informed (ผู้รับทราบ)
ผู้ที่ต้องรับรู้ความคืบหน้าหรือผลลัพธ์ของกิจกรรมนั้นๆ (เป็นการสื่อสารทางเดียว ไม่ต้องขอความเห็น)

Project Quality Management
การควบคุมคุณภาพโครงการ: มาตรฐานควบคุมคุณภาพไม่ใช่สิ่งที่จะมาตรวจสอบตอนสิ้นสุดโครงการเท่านั้น แต่ต้องฝังอยู่ในทุกข้อตกลงและทุกสถานะของกระบวนการทำงาน
 อ้างอิง: ISO/IEC 25010 (Systems and software engineering — Systems and software Quality Requirements and Evaluation) 

Quality Gate คือจุดตรวจสอบในวงจรการพัฒนาซอฟต์แวร์ที่ชิ้นงานหรือโค้ด ต้องผ่านเกณฑ์คุณภาพที่กำหนดไว้ครบถ้วน จึงจะได้รับอนุญาตให้ข้ามเฟสหรือขยับสถานะไปยังขั้นตอนต่อไปได้
ประตูควบคุมคุณภาพ (Quality Gate) คืออะไร?

แทนที่จะเลื่อนการ์ดจาก "In Progress" ไปช่อง "Done" โดยตรง เราจะเพิ่มด่านกักกันไว้ตรงกลาง:
การ์ดงานจะถูกกักไว้ที่ช่องสีแดงนี้เสมอ จนกว่าทีมจะพิสูจน์ได้ว่าโค้ดนั้นผ่านกติกาเหล็กของทีม
[ To Do ]
[ In Progress ]
[ Done ]
การตั้งประตูคุณภาพบนบอร์ด Jira / Trello

DoD: คือรายการเช็คลิสต์หรือข้อตกลงร่วมกันที่เป็นทางการของทีม เพื่อประกาศว่างานชิ้นนั้นมีความสมบูรณ์ตามมาตรฐานคุณภาพแล้วจริง ๆ ไม่ใช่คำพูดลอยๆ ของนักพัฒนาว่า "เขียนโค้ดเสร็จแล้วครับ"
💡 หัวใจของ DoD
สร้างมาตรฐานความโปร่งใส ป้องกันไม่ให้สมาชิกแอบปล่อยโค้ดที่รกรุงรัง ไร้ระเบียบ หรือยังไม่ได้ทดสอบเข้าสู่ระบบหลัก จนทำพังในภายหลัง
ทำความรู้จักกับ Definition of Done (DoD)
 อ้างอิง: Ken Schwaber and Jeff Sutherland, The Scrum Guide 

กติกาที่จะระบุไว้บนหน้าบอร์ด Jira/Trello ของกลุ่มเราในเทอมนี้:
[ ] โค้ดต้องผ่านการรีวิวตรวจสอบโดยเพื่อนร่วมทีมอย่างน้อย 1 คน (Peer Review)
[ ] ชุดทดสอบอัตโนมัติ PyTest (จากวิชา ENGSE225) ต้องผ่านไฟเขียว 100%
[ ] ต้องไม่มีการแอบกู้หนี้ทางเทคนิคเพิ่ม (เช่น ห้ามทิ้งตัวแปร Global ไร้ชื่อลึกลับไว้เพิ่มเติม)
[ ] บันทึก Change Log ประวัติการแก้ไขระบบได้รับการอัปเดตเรียบร้อย
ตัวอย่างรายการกติกาเหล็ก DoD ของทีม

กติกา DoD ในฝั่งบริหาร (SPM) จะถูกบังคับใช้จริงด้วย กลไกทางเทคนิค (SCM) ผ่านระบบของ GitHub:
1. เมื่อเดฟแก้โค้ดเสร็จ ต้องเปิด Pull Request (PR) เพื่อขอรวมสายเข้าสู่ develop
2. ระบบ GitHub จะล็อกไว้ไม่ให้รวม จนกว่าผู้มีอำนาจ (Tech Lead ตาม RACI) จะมากด Approve
3. เป็นการตรวจสอบคู่ขนานเพื่อให้ได้มาตรฐานระบบ
ความเชื่อมโยงระว่างการจัดการและเทคนิค
