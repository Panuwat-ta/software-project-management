> **คำชี้แจง:** ตอบคำถามอัตนัยโดยใช้องค์ความรู้ทางวิศวกรรมซอฟต์แวร์และมาตรฐาน ISO/IEC ในการอธิบายและวิเคราะห์อย่างมีเหตุผล (ข้อละ 10 คะแนน รวม 50 คะแนน)

## ข้อที่ 1: ประเภทการบำรุงรักษาซอฟต์แวร์ และกฎของ Lehman

*สัปดาห์ที่ 1–2*

จากกรณีศึกษาซอฟต์แวร์คลังสินค้าเดิม (app_v1.py) ที่มีปัญหาการใช้ตัวแปรระดับโลก global x และไม่มีการดักจับข้อผิดพลาด (Input Validation)

### 1.1 จำแนกประเภทการบำรุงรักษา

จงจำแนกกิจกรรมต่อไปนี้ตามมาตรฐาน ISO/IEC 14764 พร้อมอธิบายเหตุผล

- **กิจกรรม ก:** แก้โค้ดไม่ให้โปรแกรม Crash เมื่อผู้ใช้กรอกตัวอักษรในช่องจำนวนสินค้า
- **กิจกรรม ข:** เพิ่มระบบคำนวณส่วนลดสมาชิก (Member Discount) ตามความต้องการใหม่ของลูกค้า
- **กิจกรรม ค:** ปรับโครงสร้างโดยแยก `main()` เป็นโมดูลย่อยและใช้ Repository Pattern โดยผลลัพธ์ภายนอกยังเหมือนเดิม

#### คำตอบ 1.1

- **กิจกรรม ก — Corrective Maintenance:** แก้ Fault ที่ทำให้ระบบทำงานผิดหรือ Crash โดยเพิ่มการตรวจสอบ/ดักจับ input ที่ไม่ใช่ตัวเลข เพื่อให้พฤติกรรมกลับมาถูกต้อง
- **กิจกรรม ข — Perfective Maintenance:** เพิ่มความสามารถใหม่ คือ Member Discount ตามคำขอผู้ใช้ เพื่อเพิ่มคุณค่าให้ระบบ (ไม่ใช่ Adaptive เพราะสภาพแวดล้อม เช่น OS หรือฐานข้อมูล ไม่ได้เปลี่ยน)
- **กิจกรรม ค — Preventive Maintenance:** Refactoring แยก `main()` เป็นโมดูลและใช้ Repository Pattern โดยคงพฤติกรรมภายนอกไว้ เพื่อชำระ Technical Debt ลดความซับซ้อน และลดโอกาสเกิดบั๊กเมื่อต้องแก้ในอนาคต

### 1.2 กฎของ Lehman

จงอธิบาย Law of Continuing Change และ Law of Increasing Complexity โดยเชื่อมโยงกับสาเหตุที่ทำให้โค้ดคลังสินค้าเดิมยุ่งเหยิงเมื่อขาด Refactoring

#### คำตอบ 1.2

- **Law of Continuing Change:** ระบบที่ใช้งานจริง (E-type system) ต้องเปลี่ยนอย่างต่อเนื่องเพื่อรองรับความต้องการ ธุรกิจ กฎหมาย หรือเทคโนโลยีที่เปลี่ยนไป มิฉะนั้นคุณค่าของระบบจะลดลง
- **Law of Increasing Complexity:** ทุกการเปลี่ยนแปลงมีแนวโน้มเพิ่มความยุ่งเหยิงของโครงสร้าง เว้นแต่ทีมจะลงทุนควบคุมความซับซ้อน เช่น Refactoring และกำหนดโครงสร้างที่ชัดเจน
- **การเชื่อมโยง:** การเพิ่มเมนู/กฎส่วนลดลงใน `main()` เดิมเพื่อตอบสนอง Continuing Change จะเพิ่มเงื่อนไขและจุดพึ่งพา `global x` หากไม่แยกหน้าที่และห่อหุ้มข้อมูล ความซับซ้อนจะสะสมเป็น Spaghetti Code ทำให้ผลกระทบข้างเคียงและค่าใช้จ่ายในการแก้ไขเพิ่มขึ้น

## ข้อที่ 2: Program Comprehension และ Reverse Engineering

*สัปดาห์ที่ 2*

ในการทำความเข้าใจซอฟต์แวร์ Legacy ดั้งเดิมที่ขาดเอกสารประกอบ

### 2.1 Static Analysis

Static Analysis คืออะไร และมีประโยชน์อย่างไรเมื่อต้องรับช่วงดูแลระบบเก่าจากผู้อื่น?

#### คำตอบ 2.1

- **Static Analysis** คือการอ่านและวิเคราะห์ซอร์สโค้ดโดยไม่รันโปรแกรม เพื่อค้นหาโครงสร้าง ตรรกะ และจุดบกพร่อง เช่น control flow, ตัวแปรและขอบเขตของตัวแปร, call graph และ dependency
- **ประโยชน์:** ช่วยสร้าง mental model ของระบบเก่าที่ไร้เอกสาร ระบุ hotspot เช่น `main()` ที่ผูกหลายหน้าที่หรือ `global x` ที่ถูกใช้ข้ามฟังก์ชัน แล้วนำผลไปทำ DFD/แผนผลกระทบก่อนแก้จริง จึงลดโอกาส Regression

### 2.2 ผลกระทบของ Global State

จงวิเคราะห์ข้อเสียของ `global x` ในแง่ Side Effects, Analyzability และ Modifiability ตาม ISO/IEC 25010

#### คำตอบ 2.2

- **Side Effects:** ฟังก์ชันหนึ่งเขียนค่า `global x` แล้วเปลี่ยนสถานะที่ฟังก์ชันอื่นอ่านอยู่โดยไม่ประกาศผ่านพารามิเตอร์/สัญญา จึงอาจทำให้เมนูลดสต็อกทำให้การคำนวณยอดรวมผิดแบบซ่อนเร้น
- **Analyzability ลดลง:** ผู้ดูแลต้องไล่ทุกจุดที่อ่านหรือเขียนตัวแปรกลาง จึงยากที่จะอธิบายสาเหตุและขอบเขตผลกระทบของการเปลี่ยนแปลง
- **Modifiability ลดลง:** การแก้เพียงจุดเดียวเสี่ยงทำให้ฟังก์ชันที่ไม่เกี่ยวข้องพัง (Regression) ต้องทดสอบวงกว้างและแก้โค้ดได้ช้าลง การ encapsulate สถานะใน Repository ช่วยลดปัญหานี้

## ข้อที่ 3: Software Configuration Management (SCM) และ GitFlow

*สัปดาห์ที่ 3 และ 6*

### 3.1 Baseline Management

ทำไมการให้ทีม Commit และ Push เข้า `main` โดยตรงในโครงการเก่าจึงอันตราย? จงอธิบายโดยอ้างอิง Baseline Management ตาม ISO 10007

#### คำตอบ 3.1

ตาม ISO 10007, baseline คือเวอร์ชันที่ผ่านการตรวจสอบและปักหมุดเป็นจุดอ้างอิงที่เสถียร ดังนั้น `main` ควรทำหน้าที่เป็น baseline ไม่ใช่พื้นที่ทดลอง การ push ตรงข้ามขั้นตอน Configuration Control ทำให้เกิด merge conflict ในโค้ดเก่า, บั๊กเข้าสายใช้งานจริง, ประวัติ/เหตุผลของการเปลี่ยนแปลงไม่ชัด และสูญเสียจุดที่เชื่อถือได้สำหรับ rollback หรือเปรียบเทียบเวอร์ชัน

### 3.2 GitFlow และ Branch Protection

จงอธิบายหน้าที่ของ `main`, `develop` และ `feature/` branches ตาม GitFlow และอธิบายว่า Branch Protection Rules ช่วยกันโค้ดที่มีบั๊กออกจากคลังหลักอย่างไร

#### คำตอบ 3.2

- **GitFlow Architecture:**
  - `main`: เก็บเวอร์ชันที่เสถียรและพร้อมใช้งานจริง
  - `develop`: สายบูรณาการงานที่ผ่านการพัฒนารายฟีเจอร์
  - `feature/<name>`: สายแยกสำหรับฟีเจอร์หรือ Refactoring หนึ่งเรื่อง แล้วเปิด PR เพื่อรวมกลับ `develop`
- **Branch Protection Rules:** บังคับ PR, การอนุมัติจาก reviewer และ required status checks เช่น PyTest บน CI ก่อน merge จึงเกิดทั้งการตรวจโดยคนและการตรวจอัตโนมัติ; ถ้า review ยังไม่อนุมัติหรือเทสต์แดง ปุ่ม Merge จะยังใช้ไม่ได้

## ข้อที่ 4: Automated Testing และ Regression Testing

*สัปดาห์ที่ 3 และ 7*

### 4.1 Regression Testing

Regression Testing สำคัญต่อ Software Evolution อย่างไร และเหตุใดงานบำรุงรักษาควรใช้ Automated Testing เช่น PyTest มากกว่า Manual Testing?

#### คำตอบ 4.1

- **บทบาท:** เป็น safety net ที่ล็อกพฤติกรรมเดิม เช่น ผลคำนวณมูลค่าคลังสินค้า แล้วยืนยันว่าการแก้บั๊ก/Refactoring/เพิ่มส่วนลดสมาชิกไม่ทำลายพฤติกรรมที่เคยถูกต้อง
- **เหตุผลที่ควรเป็น Automated:** งานบำรุงรักษามีการเปลี่ยนโค้ดบ่อย จึงต้องรันชุดเดิมซ้ำได้รวดเร็ว สม่ำเสมอ และทำซ้ำได้ทุก PR; PyTest ลดเวลาและ human error ของ manual test และให้ผลเป็นหลักฐานใน CI

### 4.2 CI/CD Pipeline ผ่าน GitHub Actions

จงอธิบายการทำงานของ CI/CD Pipeline เมื่อเปิด Pull Request และเหตุผลที่ควรล็อกปุ่ม Merge อัตโนมัติเมื่อ PyTest ไม่ผ่าน

#### คำตอบ 4.2

- **หลักการทำงาน:** เมื่อเปิด PR, GitHub Actions สร้างสภาพแวดล้อมมาตรฐาน ติดตั้ง dependency จาก `requirements.txt` แล้วรัน PyTest เพื่อรายงานสถานะของ PR อัตโนมัติ
- **เหตุผลที่ต้องล็อกปุ่ม Merge:** ผลแดงหมายถึงมีอย่างน้อยหนึ่งพฤติกรรมไม่เป็นไปตามที่เทสต์กำหนด จึงต้องแก้และรันผ่านก่อนจึงรวมได้ การตั้ง status check เป็น required ทำให้ baseline ไม่รับโค้ดที่เสี่ยง Regression แม้ผู้พัฒนาจะทดสอบผ่านเฉพาะเครื่องตนเอง

## ข้อที่ 5: Software Quality Metrics และการประเมิน ISO/IEC 14598

*สัปดาห์ที่ 5–7*

### 5.1 Code Metrics

ในการประเมินคุณภาพ To-Be Architecture ตาม ISO/IEC 14598 จงอธิบายความหมาย ผลกระทบ และแนวทางปรับปรุงของ

- **Cyclomatic Complexity (v(G))**: คืออะไร ค่า v(G) สูงส่งผลเสียอย่างไร และลดค่าได้อย่างไร
- **Coupling Between Objects (CBO) และ High Cohesion**: เหตุใดสถาปัตยกรรมที่ดีจึงมุ่งสู่ Low Coupling, High Cohesion

#### คำตอบ 5.1

- ตามกรอบ ISO/IEC 14598 ให้ (1) กำหนดความต้องการ/เป้าหมายคุณภาพ (2) ระบุ metrics และเกณฑ์ตัดสิน (3) ออกแบบการประเมินและเตรียมเครื่องมือ แล้ว (4) สแกนโค้ดและสรุปผลเทียบเป้าหมาย To-Be
- **Cyclomatic Complexity (v(G)):** วัดจำนวนเส้นทางอิสระของ control flow จากเงื่อนไขและลูป ยิ่งสูงยิ่งต้องมี test case มากขึ้น เข้าใจและแก้ยาก; ในสไลด์ 1–10 เป็นความเสี่ยงต่ำ, 11–20 ควรเฝ้าระวัง และมากกว่า 20 บำรุงรักษายากมาก ควรแยก `main()` เป็นเมธอด/คลาสย่อย ลดเงื่อนไขซ้อน และย้าย business logic ไป Service
- **Coupling & Cohesion:**
  - **Low Coupling (CBO ต่ำ):** แต่ละคลาสพึ่งคลาสอื่นเท่าที่จำเป็นและสื่อสารผ่าน interface จึงเปลี่ยน Repository ได้โดยไม่สะเทือน UI/Business Logic; เป้าหมายตัวอย่างของสถาปัตยกรรมใหม่คือ CBO ต่อคลาสไม่เกิน 4
  - **High Cohesion:** ส่วนประกอบในโมดูลมีหน้าที่เดียวกันตามหลัก Single Responsibility เช่น Repository ดูแลการอ่าน/เขียนข้อมูล, Service ดูแลกฎธุรกิจ, UI รับ input/output จึงเข้าใจ ทดสอบ และแก้เป็นรายส่วนได้ง่าย

### 5.2 Verification และ Validation

จงเปรียบเทียบ Verification กับ Validation ในงานบำรุงรักษาซอฟต์แวร์ และยกตัวอย่างกรณีที่ระบบผ่าน Verification แต่ไม่ผ่าน Validation

#### คำตอบ 5.2

- **Verification:** ตรวจสอบว่าระบบถูกสร้างอย่างถูกต้องตามสเปกหรือไม่ (รันเทสต์ผ่าน)
- **Validation:** ตรวจสอบว่าระบบตอบสนองความต้องการใช้งานจริงของผู้ใช้หรือไม่
- **ตัวอย่าง:** โปรแกรมรันสูตรคำนวณส่วนลดถูกต้องเป๊ะตามสเปก (ผ่าน Verification) แต่ใช้งานจริงไม่ได้เพราะลูกค้าต้องการระบบที่ให้ส่วนลดซ้อนกันได้หลายชั้น (ตก Validation)
