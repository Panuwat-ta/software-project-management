Sprint 1 Tracking & Governance

การติดตามสปรินต์ที่ 1, เมทริกซ์ผู้มีส่วนได้ส่วนเสีย, การจัดซื้อ และวิเคราะห์ผลกระทบ CR-01

รวบรวมเนื้อหาครบถ้วนจากเอกสารสัปดาห์ที่ 8: Active Board, Burndown & Blocker, Stakeholder Engagement (C vs D), Procurement & Tool Log, และกระบวนการ ISO/IEC 14764 วิเคราะห์ CR-01

1. การติดตามสปรินต์ที่ 1 — Active Board & Burndown

Active Board & Work Log (ที่มา: ENGSE202 Week 8)

  • ดึงการ์ด Refactoring เข้าช่อง In Progress แล้วกด Log Work ใส่ชั่วโมงจริง (Man-Hours)
  • เส้น Burndown ขยับลงตามชั่วโมงงานที่เหลืออยู่จริง
  • ส่ง Pull Request บน GitHub โดยใส่ Jira Issue Key ในชื่อ PR (ตัวอย่างจาก transcript: ENGSE-201) แล้วสอบทานว่า Automation ขยับการ์ด In Progress → Code Review อัตโนมัติ
  • หลัก Governance: Transparency (งาน+ชั่วโมงจริงบนบอร์ด) / Inspection (ส่อง Burndown) / Adaptation (เคลียร์ Blocker ใน Daily Standup)
  • สิ่งส่งมอบ: ภาพแคปเจอร์ Sprint Burndown Chart บน Jira + รายงาน Work Log

Burndown Chart — แกน, เส้น และรูปแบบ (ENGSE202)

  • แกน X: วันทำงานใน Sprint (เช่น Day 1 ถึง Day 10)
  • แกน Y: ปริมาณงานที่เหลือ (Man-Hours หรือ Story Points)
  • Ideal Burndown Line: เส้นตรงอุดมคติจากงานรวมลงสู่ 0
  • Actual Burndown Line: เส้นจริงขยับตามการกด Log Work
รูปแบบ Burndown 3 แบบ:
  1. Ahead of Schedule — เส้น Actual อยู่ใต้ Ideal Line → ปิดงานเร็วกว่าแผน
  2. Behind Schedule — เส้น Actual อยู่เหนือ Ideal Line → ล่าช้ากว่าแผน เสี่ยงปิดไม่ทัน
  3. Scope Increase — เส้น Actual พุ่งสูงขึ้นกลาง Sprint → งานแทรก หรือเพิ่มเวลาจาก CR
หมายเหตุ: ไม่มีการระบุตัวเลขรายวัน (actual/ideal รายวัน, story points รวม, capacity ชั่วโมง) ใน transcript จึงไม่มีตารางตัวเลขรายวันในเอกสารนี้

2. Blocker, Jira Flag & Refactoring ที่ถูกติดตาม

การจัดการ Blocker / Jira Flag (ที่มา: ENGSE202 Week 8)

  • Blocker คือ: ปัญหาหรือความเสี่ยงที่เกิดจริงแล้วทำให้สมาชิกทำต่อไม่ได้
  • ตัวอย่างจาก transcript: ติดขัดเพราะไร้ Mock Data / รอ Peer Review บน GitHub นานเกิน 24 ชม.
  • บทบาท PM ใน Daily Standup: บันทึกลง Impediment Backlog แล้วรีบเข้าช่วยปลดล็อกเพื่อรักษาสปีดทีม
  • Jira Flagging: กด Add Flag บนการ์ด → การ์ดเปลี่ยนเป็นสีแดง/เหลือง มีสัญลักษณ์ธงเด่นบน Active Board → PM เข้าเคลียร์
  • ข้อบังคับ: ต้องใส่ Comment ระบุสาเหตุและชื่อผู้ที่ต้องเข้าช่วย

Refactoring ที่ถูกติดตามบนบอร์ดนี้ (ENGSE225 Week 8)

  • Branch ปฏิบัติการ: feature/refactor-core-architecture
  • 4 เทคนิค Fowler: Rename Variable/Method, Extract Function, Extract Class, Encapsulate Field
  • กฎเหล็ก: รักษา PyTest ไฟเขียว 100% ตลอดกระบวนการ
    • Baseline: pytest test_app.py ต้อง 1 passed ก่อนแตะโค้ด
    • แก้ทีละน้อยแล้วรัน pytest ซ้ำทันที
    • ไฟแดงให้ git checkout ถอยกลับ
    • ห้ามเพิ่มฟีเจอร์ใหม่ตอน Refactor

3. เมทริกซ์ผู้มีส่วนได้ส่วนเสีย — C vs D + CR-01

คำนิยามและกลุ่ม (ENGSE202 Week 8, PMBOK 7th):

  • Stakeholder: บุคคล/กลุ่ม/องค์กรที่มีผลกระทบหรือได้รับผลกระทบจากการตัดสินใจและผลลัพธ์ของโครงการ
  • Sponsor / อาจารย์: ต้องการงานเสร็จตามงบ เวลา และสเปก
  • Tech Lead / Devs: ต้องการโค้ดสะอาด ลดหนี้ทางเทคนิค
  • End-Users: ต้องการฟีเจอร์ใหม่ที่ใช้งานง่าย ไร้บั๊ก

ระดับการมีส่วนร่วม 5 ระดับ (ที่มา: ENGSE202 Week 8):

  1. Unaware — ไม่ทราบถึงการมีอยู่หรือผลกระทบโครงการ
  2. Resistant — ทราบเรื่องแต่ต่อต้าน ไม่เห็นด้วย
  3. Neutral — ทราบเรื่องแต่ไม่แสดงท่าทีหนุนหรือค้าน
  4. Supportive — ทราบเรื่องและพร้อมหนุนให้สำเร็จ
  5. Leading — มีส่วนร่วมเข้มข้น ผลักดันโครงการ
ผู้มีส่วนได้ส่วนเสีย (Stakeholder) ปัจจุบัน (Current, C) ที่ต้องการ (Desired, D) กลยุทธ์รับมือ CR-01 (จาก transcript)
Sponsor (อาจารย์) Supportive Leading รายงาน Impact Analysis
Tech Lead (ทีมงาน/เพื่อนในทีม) Leading Leading จัดสรร Refactoring
End-User (ผู้ใช้/ผู้ใช้สมมุติ) Resistant Supportive สาธิตฟีเจอร์ Barcode
การทูต CR-01: ห้ามยอมรับทันทีโดยไม่ประเมิน และห้ามปฏิเสธลูกค้ารุนแรงทันที แนวทางมืออาชีพคือใช้ Impact Analysis ชี้แจงผลกระทบเวลา/งบ แล้วนำ CR-01 ไปจัดลำดับใส่ Sprint 2 พร้อมทางเลือกขยายงบจาก Contingency Reserve หรือตัด Scope ที่ไม่สำคัญออก (+8 Man-Hours, กระทบ 2 Class, เพิ่ม PyTest 3 Cases)

5. วิเคราะห์ผลกระทบ CR-01 — Barcode & Reorder Point

ใบคำขอและกระบวนการ ISO/IEC 14764

  • CR ID: CR-01 (คำขอ: เพิ่มเก็บ Barcode และ Reorder Point)
  • Requester: อาจารย์ / Sponsor
  • ข้อบังคับ Step 1: ห้ามรับคำขอผ่านวาจา/แช็ตส่วนตัว ต้องบันทึก CR Form ชัดเจน
  • Step 1 Identification: รับและบันทึก CR Form
  • Step 2 Impact Analysis: ประเมิน Technical / Test / Cost
  • Step 3 Implementation: แตก Branch feature/cr01-barcode-reorder-point จาก develop → รัน pytest 100%
  • ผลกระทบสรุป: Cost Impact: +8 Man-Hours | Technical Impact: กระทบ 2 Class (Product, Repo) | Test Impact: เขียน PyTest เพิ่ม 3 Cases

Traceability Matrix — รายละเอียดจุดกระทบ (ENGSE225)

องค์ประกอบ จุดกระทบเชิงเทคนิค ผลกระทบด้านการทดสอบ
Class Product เพิ่ม barcode: str และ reorder_point: int เพิ่ม Unit Test ตรวจชนิดข้อมูล
InventoryRepository ปรับโครงสร้าง JSON serialization / deserialization คีย์ใหม่ เพิ่ม Test Case อ่าน/เขียนไฟล์
ConsoleUI เพิ่มช่องรับ Input Barcode และแสดงเตือน Reorder Alert ทดสอบ UI Mock Inputs
หมายเหตุ: ENGSE202 สรุปภาพรวมกระทบ 2 Class (Product, Repo) ส่วน ENGSE225 ลงรายละเอียด 3 แถวรวม ConsoleUI

6. บริบท Refactoring ก่อนรับ CR-01 & การทูต

บริบท Refactoring ก่อนรับ CR-01 (ที่มา: ENGSE225 Week 8)

  • ผ่าตัด app_v1.py บน Branch feature/refactor-core-architecture ปรับโครงสร้างภายในโดยไม่เปลี่ยนพฤติกรรมภายนอก
  • Rename Variable/Method: ชื่อลึกลับ x, a, b → Intent-Revealing (Analyzability ISO 25010)
  • Extract Function: ลด v(G) ของ main() จาก 22 → 8 เทสต์เฉพาะฟังก์ชันได้
  • Extract Class: Product (Data Model), InventoryRepository (JSON CRUD), InventoryService (Business Logic)
  • Encapsulate Field: เลิก global x; ฉีด Repository เข้า Service (Dependency Injection)
  • Baseline pytest test_app.py ต้อง 1 passed ไฟเขียว 100% ก่อนแตะโค้ด แก้ทีละน้อยแล้วรันซ้ำทันที

การทูต/การสื่อสาร และการส่งต่อสู่ SPM

  • การส่งต่อสู่ SPM: นำ Man-Hours ไปประเมินงบเพิ่มเติม ดึง Contingency Reserve และปรับการ์ดงานบน Jira
  • ไม่รับ CR-01 กลาง Sprint 1 ทันที และไม่ปฏิเสธรุนแรง
  • ชี้แจงด้วย Impact Analysis แล้วจัดลำดับเข้า Sprint 2
  • ทางเลือกที่สื่อสาร: ขยายงบจาก Contingency Reserve หรือตัด Scope ไม่สำคัญออก
