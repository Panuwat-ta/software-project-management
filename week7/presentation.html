เจาะลึกการใช้ตัวชี้วัดความซับซ้อนของโค้ด (Cyclomatic Complexity)
การวางท่อส่งมอบ CI/CD อัตโนมัติ
และการคำนวณขีดความสามารถ (Capacity) สำหรับรับงานใน Sprint 1

1. การประเมินคุณภาพ (ISO/IEC 14598)

ตัวชี้วัดเชิงปริมาณ (Quantitative Metrics) เพื่อประกันความสำเร็จของการรีแฟกเตอร์:

Cyclomatic Complexity v(G)

  • ก่อนแก้ไข: `main()` มีการใช้ if-elif-else ซ้อนกันมากกว่า 20 ชั้น เสี่ยงต่อบั๊กแฝงสูงลิบ
  • เป้าหมายใหม่: บังคับให้ฟังก์ชันย่อยลง (Modular) จนมีค่า v(G) ≤ 8 เพื่อการดูแลรักษาที่ง่ายขึ้น

Security & Reliability

  • กำจัดตัวแปร Global: เลิกใช้ global x และผูกข้อมูลเข้ากับ Class (Encapsulation)
  • ป้องกัน SQL Injection: ห้ามต่อสตริง SQL สดๆ บังคับใช้ Parameterized Query ทุกคำสั่ง (Repository)

2. ระบบควบคุมคุณภาพอัตโนมัติ (CI/CD Quality Gate)

การพึ่งพามนุษย์ตรวจสอบโค้ดเพียงอย่างเดียวอาจมีข้อผิดพลาด (Human Error) เราจึงติดตั้ง GitHub Actions ผ่านไฟล์ pytest.yml ให้ทำหน้าที่เป็น "ยามรักษาการณ์อัตโนมัติ":

  • ทำงานทุกครั้งที่ Developer สั่ง Push หรือเปิด Pull Request เข้า develop
  • โหลด requirements.txt (เช่น pytest==8.0.2) และรัน test_app.py
  • กฎเหล็ก: หากพบ Fail แม้แต่เคสเดียว ปุ่มรวมโค้ด (Merge) จะถูกปิดการใช้งานทันที ป้องกันโค้ดขยะหลุดขึ้นสู่เซิร์ฟเวอร์หลัก

Code Coverage Goal

≥ 85%

ของ Business Logic ทั้งหมด
ต้องถูกครอบคลุมโดยเทสต์
