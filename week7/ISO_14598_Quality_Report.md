# รายงานการประเมินคุณภาพ ISO/IEC 14598 (ISO/IEC 14598 Evaluation Report)

## 1. บริบทของการประเมิน (Evaluation Context)
- **ระบบเป้าหมาย**: ระบบคลังสินค้า (Inventory Management)
- **วัตถุประสงค์**: เพื่อประเมินผลการยกระดับโค้ดจากแบบเก่าใน `week-1/app_v1.py` ที่มีปัญหา (Global State, Hardcode, ขาด Validation) ไปสู่เวอร์ชันใหม่ใน `week-4/app.py` และที่จะไปต่อเป็น SQLite
- **โมเดลคุณภาพอ้างอิง (ISO 25010)**: มุ่งเน้นไปที่ **Maintainability (ความสามารถในการบำรุงรักษา)** และ **Reliability (ความน่าเชื่อถือ/เสถียรภาพ)**

## 2. เป้าหมายตัวชี้วัดเชิงปริมาณ (Quantitative Target Metrics)

เพื่อยืนยันว่าการเปลี่ยนโครงสร้างด้วยการทำ OOP และ Input Validation ประสบความสำเร็จ เราได้กำหนดตัวชี้วัดดังนี้:

| ดัชนีชี้วัดคุณภาพโค้ด | สถานะโค้ดดั้งเดิม (`app_v1.py`) | เป้าหมายที่คาดหวังในเวอร์ชันล่าสุด |
| :--- | :--- | :--- |
| **Max Cyclomatic Complexity $v(G)$** | สูงเกินเกณฑ์ (มี `if-elif-else` ซ้อนกันมากกว่า 20 จุดใน `main()`) 🔴 | แยกย่อยฟังก์ชัน $\le 8$ 🟢 |
| **ความปลอดภัยของข้อมูล (Data Security)** | สคริปต์ล่มทันทีถ้ากรอกตัวอักษรแทนตัวเลข | มีระบบดักจับ (Try-Except Validation) |
| **การใช้ Global State** | พึ่งพา `global x` ทุกฟังก์ชัน | ยกเลิกการใช้ 100% เปลี่ยนเป็น Class Instances |
| **Code Coverage (ทดสอบโดย QA)** | 0% (ไม่มีสคริปต์เทสต์) | ผ่านการทดสอบจาก `test_app.py` $\ge 85\%$ |
| **SQL Injection Vulnerability** | N/A (ใช้ JSON) | ต้องใช้ Parameterized Query ป้องกัน 100% (เมื่อใช้ SQLite) |

## 3. สภาพแวดล้อมการประเมินและท่อส่ง (CI/CD Quality Gate)
- การประเมินคุณภาพของโค้ดและบั๊กจะเกิดขึ้นบน **GitHub Actions (CI/CD Pipeline)** โดยอัตโนมัติ
- ทุกครั้งที่ **Developer** เปิด Pull Request เพื่อขอแก้ไขงาน:
  1. ระบบจะโหลดไฟล์ `requirements.txt` ที่ล็อกเวอร์ชันเครื่องมือ (เช่น `pytest==8.0.2`)
  2. รันสคริปต์ `test_app.py` ที่เขียนโดย **QA**
  3. หากพบว่าเทสต์ไม่ผ่าน (รันพัง หรือผลการคำนวณผิดพลาด) ปุ่มรวมโค้ดจะถูกล็อกทันที เพื่อให้ **Tech Lead** ไม่เสียเวลามารีวิวโค้ดที่ยังพังอยู่
