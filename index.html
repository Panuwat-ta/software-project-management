วัตถุประสงค์โครงการ (Project Objectives)

1. ปรับปรุงเสถียรภาพการทำงาน
ทำให้ระบบทนทานต่อข้อผิดพลาด (Fault Tolerance) ป้องกันโปรแกรมล่มจากการรับข้อมูลนำเข้าผิดประเภท (Crash Prevention) และดักจับค่าขยะหรือตัวเลขติดลบ
Stability Crash Prevention
2. ปรับปรุงโครงสร้างโค้ด
ทำความสะอาดโค้ดดั้งเดิม (Clean Code) กำจัดการใช้ตัวแปรโกลบอล x แยก Business Logic ออกจาก Presentation Layer และจัดระบบตามหลัก OOP
Architecture PEP 8 / OOP
3. รักษาความสมบูรณ์ของข้อมูล
ปรับปรุงกระบวนการบันทึกไฟล์ JSON ให้ปลอดภัยด้วยวิธี Safe Atomic Write (เขียนลง Temp แล้วสลับด้วย os.replace) ป้องกันข้อมูลสูญหาย
Integrity Atomic Write
4. สร้างระบบทดสอบอัตโนมัติ
จัดทำชุดทดสอบอัตโนมัติด้วย PyTest ครอบคลุมฟังก์ชันคำนวณและกรณีขอบเขต (Boundary Cases) เพื่อทำ Regression Testing ป้องกันข้อผิดพลาดเดิมย้อนกลับมา
Testing PyTest 100%

คลังเอกสารรายสัปดาห์ (Weeks 1 - 12)

สรุปหลักฐาน รายงานการวิเคราะห์ และแผนงานในแต่ละสัปดาห์ พร้อมสไลด์นำเสนอประกอบ ตัวเลขงบคนละชุดมีฐานต่างกัน: 39,100 = W5 worksheet · 18,823 = W7 baseline ที่อนุมัติ · 15,525 = ขอบเขต EVM (ทั้งหมดสมมติเพื่อการเรียน)

สัปดาห์ที่ 1: วางแผนและทบทวนระบบเดิม

อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 2: วิเคราะห์และออกแบบโครงสร้างใหม่
วิเคราะห์ Hotspot, DFD Level 1, Static Code Analysis (LOC 99, CC 14) และจัดทำพิมพ์เขียว Blueprint
อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 3: ลงมือพัฒนาและกำหนดเกณฑ์งาน
พัฒนา app_v2.py ตามสถาปัตยกรรมใหม่ กำหนดเกณฑ์ Definition of Done (DoD) และ RACI Matrix
อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 4: ทดสอบระบบและปรับปรุงโค้ด
ทดสอบ PyTest 5 ผ่าน พัฒนาระบบรายงานผล test.json และปรับปรุงความสมบูรณ์ของ app.py
อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 5: สถาปัตยกรรมและงบประมาณ
ออกแบบ As-is vs To-be Architecture, ประเมินคุณภาพ ISO 25010 และจัดทำ Budget Worksheet (39,100 THB ข้อมูลสมมติเพื่อการเรียน)
อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 6: เกณฑ์การสื่อสารและ To-Be Architecture
กำหนด Communication Matrix, เกณฑ์ DoR/DoD และออกแบบ To-Be Architecture รองรับ SQLite และ Member System (แบบออกแบบเท่านั้น)
อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 7: ต้นทุนงบประมาณ Baseline และคุณภาพ
อนุมัติ Cost Baseline 18,823 THB (ข้อมูลสมมติเพื่อการเรียน) และรายงานคุณภาพ ISO/IEC 14598 กำหนดท่อส่ง CI/CD
อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 8: คำขอ CR-01 และการติดตามงาน
วิเคราะห์ผลกระทบ CR-01 Barcode & Reorder Point (+8 Man-Hours ข้อมูลสมมติเพื่อการเรียน) และติดตามผ่าน Burndown บน Jira
อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 9: วิเคราะห์ EVM และส่งต่องาน
สรุป EVM Sprint 1: SV -1,000, CV -1,200 (ข้อมูลสมมติเพื่อการเรียน), ถอดบทเรียน Retrospective และวางแผนเปิด Sprint 2

สัปดาห์ที่ 10: คำขอฉุกเฉิน CR-02 และแก้ BUG-101
อนุมัติ CR-02 CSV Export ผ่าน CCB ดึงเงินสำรอง 1,350 THB (ข้อมูลสมมติเพื่อการเรียน) และแก้ BUG-101 KeyError barcode ด้วย 5 Whys
อ่านเอกสาร → สไลด์บรรยาย →
สัปดาห์ที่ 11: การปรับโค้ดแข็งแกร่งและแช่แข็งขอบเขต
