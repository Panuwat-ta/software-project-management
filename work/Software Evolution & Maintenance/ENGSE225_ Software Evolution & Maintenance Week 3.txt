"Establishing stability, traceability, and safety nets in evolving codebases"

เข้าใจและประยุกต์ใช้ระบบ Software Configuration Management (SCM) ตามกรอบมาตรฐานสากล
ออกแบบการแบ่งสายโค้ด (Branching Strategy) เพื่อรองรับการทำงานเป็นทีมบนโปรเจกต์เดิม
สร้างเกราะป้องกัน Side Effects ด้วยระบบ Automated Regression Testing โดยใช้ PyTest
เป้าหมายประจำสัปดาห์ที่ 3

SCM คือระเบียบปฏิบัติทางวิศวกรรมซอฟต์แวร์ในการควบคุม ติดตาม และจัดการการเปลี่ยนแปลงของชิ้นงาน (Artifacts) ทั้งหมดที่เกิดขึ้นในวงจรชีวิตซอฟต์แวร์
🎯 วัตถุประสงค์หลักของ SCM
Traceability: ย้อนรอยได้ว่าใคร แก้ไขอะไร เมื่อไหร่ และทำไม
Reproducibility: สามารถกู้คืนระบบกลับไป ณ เวอร์ชันใดในอดีตก็ได้
Integrity: มั่นใจได้ว่าชิ้นงานซอฟต์แวร์ไม่มีการสูญหายหรือถูกทับซ้อน
Software Configuration Management คืออะไร?
 อ้างอิง: IEEE Std 828-2012 (IEEE Standard for Configuration Management in Systems and Software Engineering) 

มาตรฐาน ISO 10007:2017 ให้หลักเกณฑ์สำหรับการจัดการคอนฟิกูเรชันในองค์กร โดยแบ่งองค์ประกอบสำคัญในพาร์ทเทคนิคซอฟต์แวร์ไว้ดังนี้:
เมื่อนำมาใช้กับงานซอฟต์แวร์ จะถูกสะท้อนออกผ่าน 3 เสาหลัก: Version Control, Baseline และ Change Log
มาตรฐาน ISO 10007 ในงานวิศวกรรมซอฟต์แวร์
 อ้างอิง: ISO 10007:2017 (Quality management — Guidelines for configuration management) 

1. Version Control
ระบบควบคุมการปรับปรุงชุดคำสั่ง จัดเก็บประวัติทุก Commit (เช่น การใช้ Git/GitHub)
2. Baseline Management
การปักหมุดเวอร์ชันที่เสถียรและผ่านการตรวจสอบแล้ว เพื่อใช้เป็นจุดอ้างอิงในการพัฒนาต่อยอด
3. Change Log
บันทึกประวัติการเปลี่ยนแปลงอย่างเป็นระบบ เพื่อแจ้งให้ผู้มีส่วนได้ส่วนเสียทราบเหตุผลการแก้ไข
3 เสาหลักของการควบคุมทางเทคนิค

ในโครงการ Legacy (เช่น โค้ดคลังสินค้า v1.0 ที่มีหนี้ทางเทคนิคสูง) การปล่อยให้สมาชิก 4-5 คนกด Push โค้ดเข้าสาย main โดยตรง จะทำให้เกิดหายนะดังนี้:
💥 Merge Conflicts รุนแรง: ต่างคนต่างแก้ฟังก์ชัน main() ยาวเหยียดตัวเดียวกัน เมื่อรวมโค้ดจะพันกัน
🛑 Production Breakage: บั๊กของคนหนึ่งจะทำให้โปรแกรมของเพื่อนทุกคนพังและรันไม่ได้ทันที
📉 Loss of Baseline: สูญเสียเวอร์ชันเดิมที่รันผ่านไปอย่างกู้คืนยาก
ทำไมการรุมแก้โค้ดที่สาย main ถึงอันตราย?

GitFlow Branching Model
กลยุทธ์การแยกสายงาน: ออกแบบมาเพื่อแบ่งแยกหน้าที่ของแต่ละสายโค้ดให้ชัดเจน ช่วยให้การทำงานร่วมกันเป็นทีมมีความเป็นระเบียบและปลอดภัยสูง
เราจะใช้ GitFlow เบื้องต้นแบ่งสายงานเป็น 3 ระดับหลัก: main, develop, และ feature/
 อ้างอิง: Vincent Driessen (A successful Git branching model) 

•
🥇 main (หรือ master): เก็บโค้ดที่ เสถียรที่สุด 100% เท่านั้น ห้ามแก้ไขโดยตรงเด็ดขาด โค้ดตรงนี้พร้อมส่งมอบให้ลูกค้า
•
🥈 develop: สายหลักสำหรับการบูรณาการ โค้ดฟีเจอร์ใหม่ที่พัฒนาเสร็จแล้วจะถูกนำมารวมที่นี่เพื่อทำ Integration Test ร่วมกัน
•
🥉 feature/something: สายแยกชิ้นงานย่อย สมาชิกแต่ละคนแตกสายนี้ออกจาก develop เพื่อไปทำงานของตน (เช่น feature/member-discount) เมื่อทำเสร็จค่อยทำ Pull Request กลับเข้าสู่ develop
เจาะลึกบทบาทหน้าที่ของแต่ละ Branch

"การทดสอบซ้ำเพื่อให้มั่นใจ"
คือการทดสอบซอฟต์แวร์ในส่วนที่ ไม่ได้แก้ไข เพื่อให้มั่นใจว่าการปรับเปลี่ยนระบบในจุดหนึ่ง (เช่น แก้บั๊กสต็อก) จะไม่ส่งผลข้างเคียง (Side Effects) ทำลายตรรกะเดิมในจุดอื่นให้พังทลายลง
"เกราะป้องกันระบบเดิม ยามเราต่อเติมฟีเจอร์ใหม่"
ทำความรู้จักกับ Regression Testing
 อ้างอิง: Ian Sommerville, Software Engineering, 10th Edition 

ในโปรเจกต์วิวัฒนาการซอฟต์แวร์ ทุกครั้งที่มีการ Commit โค้ดใหม่ เราต้องทำการรัน Regression Test ทันที หากใช้คนคลิกทดสอบเองด้วยมือ (Manual) จะเกิดปัญหาดังนี้:
❌ Manual Testing Problems
ใช้เวลามาก, เกิด Human Error ได้ง่าย, คนมักจะเหนื่อยและข้ามการทดสอบบางจุดไป
🟢 Automated Testing Benefits
เขียนชุดทดสอบ (Script) ไว้เพียงครั้งเดียว สามารถกดรันซ้ำกี่หมื่นครั้งก็ได้ในเวลาไม่กี่วินาที รู้ผลบั๊กทันที
ทำไมงานบำรุงรักษาต้องเป็น "Automated"?

PyTest เป็น Testing Framework ระดับอุตสาหกรรมที่เป็นที่นิยมสูงสุดในระบบนิเวศของภาษา Python มีจุดเด่นคือเขียนง่าย ใช้คำสั่งมาตรฐานอย่าง assert ในการตรวจสอบความถูกต้อง
เราจะนำ PyTest มาใช้เพื่อทำการ "ล็อกพฤติกรรมดั้งเดิม" ของฟังก์ชันคำนวณมูลค่าคลังสินค้าเอาไว้ก่อนทำการปรับโครงสร้างโค้ด
ระบบทดสอบอัตโนมัติด้วย PyTest

ท่อนโค้ดตรรกะคำนวณมูลค่ารวมคลังสินค้าเดิม (Choice 4) ที่เราต้องการสร้างเกราะป้องกัน:
⚠️ ความเสี่ยง: หากสัปดาห์หน้าเราเปลี่ยนโครงสร้างตัวแปร x ฟังก์ชันคูณบรรทัดนี้เสี่ยงพังสูงสุด!
ส่องฟังก์ชันเป้าหมายที่จะล็อกพฤติกรรม

เราแยกสร้างไฟล์ใหม่ชื่อ test_app.py เพื่อทำ Automated Test โดยจำลองข้อมูลคลังสินค้าขึ้นมาทดสอบความถูกต้องของการคำนวณ:
ตัวอย่างการเขียนสคริปต์ทดสอบ (1/2)

ในเทอร์มินอล (Terminal) ของนักศึกษา ให้พิมพ์คำสั่งด้านล่างนี้ ระบบจะค้นหาและรันไฟล์ที่มีขึ้นต้นด้วย test_ ทั้งหมดโดยอัตโนมัติ:
สัญลักษณ์ . (จุดสีเขียว) หรือข้อความ passed หมายถึง ตรรกะเดิมยังคงปลอดภัย 100%
วิธีสั่งรันและดูผลการทดสอบ (2/2)

สมมุติว่าสมาชิกคนหนึ่งไปแก้ไขสูตรคำนวณผิดพลาดในสัปดาห์หน้า เมื่อกดรัน pytest เกราะป้องกันจะส่งสัญญาณเตือนภัยทันที:
สัญญาณ F (Failed) บอกโปรเจกต์แมเนเจอร์ทันทีว่า: "ห้ามรวมโค้ดชิ้นนี้เข้า develop เด็ดขาด เพราะทำระบบเดิมพัง!"
เมื่อเกราะป้องกันตรวจเจอความเสียหาย

กระบวนการผสานเครื่องมือเพื่อสร้างท่อพัฒนาที่ได้มาตรฐานและปลอดภัยสูง:
"ห้ามทำการอนุมัติรวมสายโค้ด (Pull Request) หากชุดทดสอบอัตโนมัติยังไม่ขึ้นไฟเขียวทั้งหมด"
การเชื่อมท่อความปลอดภัย (SCM + Testing)

ขั้นตอนการลงมือทำในห้องปฏิบัติการวันนี้:
1.
สร้างองค์กรและกลุ่มคลังเก็บซอร์สโค้ด (GitHub Repository) ประจำกลุ่ม
2.
ติดตั้งโครงสร้างสายงาน GitFlow (แตกสาย develop และมอบหมาย feature/ ให้สมาชิกแต่ละคน)
3.
เขียนไฟล์สคริปต์ทดสอบ test_app.py ด้วย PyTest เพื่อล็อกตรรกะเมนูคำนวณมูลค่ารวม
4.
ทดสอบกดสั่งรันในคอมพิวเตอร์ตนเองให้ผ่านไฟเขียว ก่อนเริ่ม Push ขึ้นระบบคลาวด์คลังโค้ด
