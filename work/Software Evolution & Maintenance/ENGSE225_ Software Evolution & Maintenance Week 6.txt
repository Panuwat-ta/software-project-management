ENGINEERING TRANSFORMATION SOFTWARE RE-ENGINEERING CONCEPT
ทำความรู้จักกับ Software Re-engineering

การ Re-engineer ไม่ใช่การเดาโครงสร้างใหม่ตามใจชอบ แต่ต้องอ้างอิง Software Design Patterns มาตรฐานสากล:
1. Repository Pattern
แก้ปัญหาการจัดการข้อมูลกระจัดกระจาย คั่นกลางระหว่าง Business Logic กับ Data Storage
2. Singleton Pattern
แก้ปัญหาภัยร้ายจาก Global State (global x) คุมการเข้าถึงทรัพยากรกลางจุดเดียว
3. Factory Pattern
แก้ปัญหาการสร้างวัตถุซับซ้อน แยกตรรกะ Object Creation ออกจากส่วนเรียกใช้งาน
STANDARD ARCHITECTURE FRAMEWORK DESIGN PATTERNS IN MAINTENANCE

ปัญหาในโค้ดเดิม (As-Is)
เมนูสั่งสินค้าแอบอ่าน/เขียนไฟล์ data.json โดยตรง
หากเปลี่ยนไปใช้ SQL Database โครงสร้างระบบจะพังทลายทันที

TARGET ARCHITECTURE 1 REPOSITORY PATTERN MECHANICS
เจาะลึก Pattern 1: Repository Pattern

ปัญหาในโค้ดเดิม (As-Is)
ใช้ตัวแปรระดับโลก global x ที่ฟังก์ชันไหนก็แอบแก้ไขได้
ก่อให้เกิด Side Effects ร้ายแรงที่ยากแก่การติดตามแก้ไข
การแก้ด้วย Singleton Pattern
ประกันว่าคลาสจัดการข้อมูลจะมีเพียง Single Instance เดียว
ควบคุมจุดเข้าถึงผ่าน DatabaseContext.getInstance() อย่างปลอดภัย

ขาด Data Validation และเสี่ยงต่อชนิดข้อมูลผิดพลาด

SOFTWARE PRODUCT EVALUATION STANDARD ISO/IEC 14598 STANDARD
มาตรฐานประเมินซอฟต์แวร์ ISO 14598

1. Establish Req.
กำหนดวัตถุประสงค์และเป้าหมายคุณภาพซอฟต์แวร์
2. Specify Eval.
เลือกตัวชี้วัด (Metrics) และเกณฑ์ตัดสิน (Thresholds)
3. Design Eval.
วางแผนการทดสอบและจัดเตรียมเครื่องมือสแกน
4. Execute Eval.
รันการทดสอบ สแกนโค้ด และสรุปผลประเมิน
EVALUATION METHODOLOGY 4-STEP EVALUATION FRAMEWORK
กรอบการประเมิน 4 ขั้นตาม ISO 14598

ในขั้นตอน Specify Evaluation (ISO 14598) เราใช้เครื่องมือสแกนตัวชี้วัดทางเทคนิคเชิงปริมาณ:
Cyclomatic Complexity
วัดความซับซ้อนของลูปและเส้นทางเงื่อนไข (Control Flow) ในฟังก์ชัน
Coupling (CBO)
วัดระดับการพึ่งพาอาศัยกันระหว่างคลาส (Coupling Between Objects)
Cohesion (LACK)
วัดความยึดเหนี่ยวของหน้าที่ภายในโมดูล (Lack of Cohesion in Methods)
QUANTITATIVE CODE ANALYSIS CORE TECHNICAL CODE METRICS
การกำหนดตัวชี้วัด Code Metrics

สูตรคำนวณความซับซ้อนทางตรรกะ Control Flow Graph:
1 - 10: โค้ดสะอาด ความเสี่ยงต่ำ (Target To-Be)
11 - 20: ความซับซ้อนปานกลาง ต้องเฝ้าระวัง
> 20: ความซับซ้อนสูงมาก บำรุงรักษายาก (As-Is app_v1.py)
LOGICAL COMPLEXITY METRIC CYCLOMATIC COMPLEXITY V(G)
เจาะลึก Cyclomatic Complexity v(G)

High Cohesion (สิ่งที่ต้องการ)
คลาสหนึ่งคลาสควรทำหน้าที่เดียวอย่างกระจ่างแจ้ง (Single Responsibility Principle)
ลดความสับสนในการทำงาน และทำให้แก้ไขโค้ดเฉพาะจุดได้ง่าย
Low Coupling (สิ่งที่ต้องการ)
คลาสต่างๆ ควรเชื่อมต่อกันผ่าน Interface เพื่อให้แก้จุดหนึ่งแล้วไม่สะเทือนจุดอื่น
การทำ Re-engineering ตาม Design Patterns จะช่วยลด Coupling โดยตรง
OBJECT-ORIENTED METRICS COUPLING VS. COHESION PRINCIPLES
ตัวชี้วัด Coupling และ Cohesion

ขั้นตอน 2: ตั้ง Branch Protection

พิสูจน์ฝั่งไฟแดง (Locked)
แตกสาย feature/test-gate แล้ว Push โค้ดที่ทำ PyTest พังขึ้นไป เปิด Pull Request เข้า develop

พิสูจน์ฝั่งไฟเขียว (Unlocked)
