การควบคุมขอบเขตในโครงการ Brownfield

Work Breakdown Structure
WBS คืออะไร: คือการสลายโครงการใหญ่ที่ซับซ้อน ให้กลายเป็นโครงสร้างลำดับชั้นของ "ชิ้นงานย่อย" (Work Packages) ที่สามารถจัดการ วัดผล และมอบหมายให้คนในทีมรับผิดชอบได้อย่างชัดเจน
"ถ้าคุณไม่สามารถแตกงานชิ้นนั้นออกเป็นงานย่อยได้ แสดงว่าคุณยังไม่เข้าใจงานชิ้นนั้นจริง ๆ"

ประโยชน์สูงสุดของการทำ WBS ในระดับวิศวกรรมซอฟต์แวร์:
1. เพื่อความโปร่งใส (Visibility)
ทุกคนในทีมเห็นว่าก่อนจะเสร็จ 1 ฟีเจอร์ ต้องผ่านขั้นตอนทางวิศวกรรมอะไรบ้าง ไม่ใช่การเดา
2. ลดความซับซ้อน (Manageability)
การเขียนโค้ด 1,000 บรรทัดน่ากลัว แต่การแบ่งไปแก้บั๊กวันละ 3 จุดนั้นเป็นไปได้และกดดันน้อยกว่า
3. ติดตามผลได้จริง (Trackability)
สามารถนำไปตั้งค่าเป็นการ์ดงานบนบอร์ด Jira / Trello เพื่อเลื่อนสถานะได้ง่าย
ทำไมเราต้องแบ่งงานออกเป็นชิ้นเล็กๆ?

เมื่อลูกค้าสั่ง: "เพิ่มระบบสมาชิกลดราคา (Member Discount) ในระบบเดิม"
📦 โปรเจกต์ปรับปรุงระบบคลังสินค้า v1.1
🔹 1. เฟสขุดค้นและเตรียมระบบ (Archeology & SCM)
🔹 2. เฟสลดความเสี่ยงเดิม (Preventive & Testing)
🔹 3. เฟสเพิ่มฟีเจอร์ใหม่ (Evolution)
○
1.1 ทำ Static Analysis และวาด Data Flow Diagram (DFD) เพื่อหาจุดเสี่ยง
○
1.2 ติดตั้ง Git/GitHub Repository และตั้งกฎ Branching Strategy
○
2.1 เขียน Unit Test ครอบคลุมฟังก์ชันการตัดสต็อกเดิม (ป้องกันระบบพังพินาศภายหลัง)
○
2.2 ทำ Refactoring เปลี่ยนชื่อตัวแปรลึกลับ (เช่น จาก x เป็น inventory)
○
3.1 ออกแบบโครงสร้างข้อมูลรองรับ Member ID และเปอร์เซ็นต์ส่วนลด
○
3.2 พัฒนาเมนูคำนวณราคาสุทธิหักส่วนลดสมาชิก
ตัวอย่างการทำ WBS โครงการคลังสินค้าเดิม

"เวลาในการเขียน ≠ เวลาในการแก้"
ใน Greenfield โปรเจกต์ ความเร็วขึ้นอยู่กับความสามารถของนักพัฒนา แต่ใน Brownfield โปรเจกต์ ความเร็วถูกตรึงไว้กับคุณภาพของโค้ดเก่า
การประมาณการเวลาเมื่อยุ่งกับ Legacy Code

ในโลกการบริหารโครงการ เราแบ่งประเภทของสิ่งที่จะพบเจอออกเป็น:
👉 ข้อแนะนำ: สำหรับโปรเจกต์ซอฟต์แวร์เก่า ให้คูณค่าเผื่อความเสี่ยง (Buffer) 1.5x ถึง 2.0x จากเวลาประเมินปกติ
Known-Knowns
ฟีเจอร์ใหม่ที่เราเคยเขียนมาแล้ว รู้แน่ชัดว่าใช้เวลาเท่าไร
Known-Unknowns
รู้ว่าเราไม่รู้สิ่งใด เช่น รู้ว่าต้องเชื่อมระบบกับฐานข้อมูลใหม่ แต่ยังไม่เคยเปิดดูคู่มือ
Unknown-Unknowns
ความเสี่ยงมืดที่ซ่อนอยู่ในโค้ดเก่า แกะแล้วถึงเจอ บั๊กซ้อนบั๊กที่ไม่มีเอกสารบอกไว้ก่อน
การเผื่อเวลาสำหรับ "ความไม่รู้"

Risk Management: คือกระบวนการเชิงรุกในการระบุ ประเมิน และเตรียมแผนรับมือกับสิ่งไม่คาดฝันล่วงหน้า ก่อนที่มันจะเปลี่ยนสภาพกลายเป็น "ปัญหาจริง" (Issue) ที่ทำลายโครงการ
การระบุ (Identify): มีอะไรในโค้ดเก่าที่จะทำเราพัง?
การประเมิน (Assess): โอกาสเกิดสูงไหม? พังรุนแรงรึเปล่า?
การรับมือ (Mitigate): มีแผนป้องกันอย่างไร?
การบริหารความเสี่ยงเชิงเทคนิค

ตารางประเมินระดับความรุนแรงของความเสี่ยง คำนวณจากสูตร: ระดับความเสี่ยง = โอกาสเกิด (Likelihood) × ผลกระทบ (Impact)
งานของ Project Manager คือการพยายามย้ายความเสี่ยงจากโซนสีแดง (Critical) ลงมาสู่โซนสีเขียว (Low) ให้ได้
ทำความรู้จักกับ Risk Matrix

สถานการณ์ความเสี่ยงทางเทคนิค (Technical Risk Case)
"เมื่อเข้าไปแก้ไขโค้ดในเมนูเพิ่ม/ลดสต็อก (Choice 2 & 3) แล้วส่งผลกระทบข้างเคียงให้ฟังก์ชันคำนวณมูลค่ารวมคลังสินค้า (Choice 4) ทำงานผิดพลาดหรือคำนวณเพี้ยน"
สาเหตุทางเทคนิค: เพราะระบบเดิมใช้ Global State (ตัวแปร x) ผูกมัดอยู่ทุกฟังก์ชันอย่างไร้ระเบียบ การขยับหนึ่งจุดย่อมสะเทือนถึงดวงดาว
กรณีศึกษา: ความเสี่ยงจากระบบคลังสินค้าเดิม

เมื่อพบความเสี่ยงระดับสูงจากสไลด์ที่แล้ว ทีมงานต้องกำหนดมาตรการป้องกันทันที:
ความเสี่ยงที่ระบุ
ระดับดั้งเดิม
แผนรับมือ/ป้องกัน (Mitigation Plan)
ระดับที่เหลืออยู่
แก้ไขสต็อกแล้วฟังก์ชันคำนวณยอดรวมเพี้ยน
High
เขียนระบบ Automated Unit Test ทดสอบฟังก์ชันคำนวณยอดรวมทุกครั้งที่มีการเปลี่ยนโค้ดส่วนอื่น และทำ Refactoring แยก Scope ตัวแปร
Low
การเขียนแผนบรรเทาความเสี่ยง (Mitigation Plan)

เพื่อนำแผนงานที่แตกย่อยไปปฏิบัติจริง ให้โปรเจกต์แมเนเจอร์ของกลุ่มนำข้อมูล WBS ไปกรอกลงระบบ Kanban Board:
To Do: งานทั้งหมดที่แตกมาจาก WBS
In Progress: งานที่สมาชิกกำลังทำ (จำกัดไม่ให้ล้นมือ)
Review: โค้ดที่เขียนเสร็จและกำลังรอตรวจคุณภาพ
Done: งานที่ผ่านการทดสอบและสมบูรณ์
